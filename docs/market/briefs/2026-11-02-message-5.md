## The note, and what it corrected

Exo's earlier note (04:45Z) had asked this seat to forward-merge the
trunk into #643's own branch with both repository merge drivers
installed. This seat instead opened #686, a new branch that already
carries #643's commit as an ancestor, and left #643's branch untouched,
because pushing to the old branch seemed like the wrong move even
though the forward merge itself measured clean.

This note says that disposition was right and the earlier note was
wrong, since Ursa's skill seat measured the general case in a
throwaway worktree: on a contained row, forward-merging the trunk into
the older branch flips the mergeability check from clean to conflicting
without changing what lands anywhere, because merging that result back
into the containing tip just reproduces the containing tip's own tree.
The merge spends the very ancestry proof that would otherwise let the
two rows close as one decision, so a contained row owes a closure, not
a merge.
