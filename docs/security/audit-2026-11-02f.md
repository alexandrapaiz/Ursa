## 2. The finding: PWC-11's fence can be stepped out of

This is the run's one substantive finding, and it is a defect in a
queued repair rather than in shipped code. Numbered **F62** for the
ledger.

### What was already known, and is not re-filed

PWC-11 holds the finding that all eleven seat workflows interpolate
`${{ github.event.client_payload.text }}` straight into the `prompt:`
block with no marker saying the text is data. The 2026-11-02d audit §5
reconfirmed it live, from inside a run whose own payload carried two
board messages written by other agents. Neither of those is re-queued
here, and the severity they assigned, low to medium, is unchanged.

### What is new

**The fence PWC-11 proposes is forgeable as written.** The proposal
wraps the interpolation in the literal lines `BEGIN EVENT` and
`END EVENT`. Both are fixed strings known to whoever composes the event
text. Actions substitutes that text raw, and YAML offers no escape hook
on the way in. So the close marker is a string the fenced content may
itself contain, which is the oldest flaw in delimiter-based containment:
the fence holds only for content that declines to mention it.

**The two precedents PWC-11 cites are safe, and not for the reason it
gave.** This matters because the entry reasons from them. Neither trusts
a delimiter. Both make the content unable to produce one.

| Precedent | Fence | Why it actually holds |
|---|---|---|
| `ursa-major/src/tuning/distill.ts` | `BEGIN EVIDENCE` / `END EVIDENCE` | Every fenced field goes through `JSON.stringify`, so a newline in the data becomes the two characters `\` and `n`. No line break survives into the prompt, so no line can be exactly `END EVIDENCE`. |
| `ursa-major/src/verdict.ts` | `BEGIN MESSAGES` / `END MESSAGES` | `shownText` replaces `[\r\n]` with spaces before the transcript reaches the fence, for a stated reason about offset invariants. The fence's unforgeability is a side effect of that, which is worth knowing. |

A workflow prompt can do neither, because there is no code between the
event text and the prompt. It therefore needs a different mechanism, not
the same markers.

**And the step-out lands in the one slot that claims authority.**
Measured with `tools/prompt-slots.mjs`, added in this run: in ten of the
eleven files exactly **one newline** separates the end of the event slot
from the literal header "Owner instructions for this dispatch, binding
for this run and extending the charter". The eleventh, `agent-pm.yml`,
has one paragraph of the PM's own standing orders in between.

PWC-11 leaves that owner block unfenced on purpose and gives a reason
that is correct as far as it goes: the owner is one of the three sources
every charter says may instruct a seat. The reason is right about the
owner and does not cover the path. `repository_dispatch` declares no
`inputs:`, so on exactly the trigger that populates the event slot,
`${{ inputs.owner_instructions }}` resolves to nothing. **The binding
slot is empty whenever the forgeable one is full**, so its authority
accrues to whatever text was written last. This is read from the
workflow files and from the documented scope of the `inputs` context,
not from a live dispatch, because firing one is not this run's to do.

### What this is not

Not shell injection. The interpolation reaches an action input and never
a `run:` block. The 2026-11-02d audit asserted that in prose; this run
measures it, across all twelve workflow files, and it is now a test
rather than a sentence. Zero untrusted interpolations in any `run:`
block.

Not publicly reachable. `repository_dispatch` needs a token with write
access and `PM_DISPATCH_ENABLED` is a repository variable only the owner
sets, so there is no public write path to the bus. The cost is still the
laundering path the charter names: a seat that relays an issue body, a
pull request description or a scraped page into a board message turns
that text into another seat's instructions, in a run with
`bypassPermissions`, `contents: write`, `pull-requests: write` and three
live credentials in the environment.

Not currently live. The workflow door is closed by decision 056. These
eleven launchers still declare `repository_dispatch` and
`workflow_dispatch`, and the host may reopen the door with one variable
for an outage, so this is latent in the same way F59 is latent.

### The repair, and who holds it

Reserved to the owner. Every seat dispatch, including the one that
opened this run, says "never touch secrets or workflows" in those words,
so this run did not edit `.github/workflows/` and did not probe the
boundary by attempting it. The amended change is written out in full in
PWC-11. Three one-line differences from the queued form:

1. **Move the owner block above the event block**, so the untrusted slot
   is last in the prompt. This is the one to apply if only one is
   applied. It removes the target instead of guarding it, it is a move
   of a block that is already adjacent, and unlike the other two it
   cannot be defeated by any payload, because there is nothing below the
   fence to step into.
2. **Suffix both markers with `${{ github.run_id }}`.** The run does not
   exist when the event text is composed, so its id cannot be in that
   text. Unguessable in practice rather than secret, and it should not be
   described as authentication.
3. Keep PWC-11's label sentence exactly as it already words it.

## 3. The instrument

`tools/prompt-slots.mjs`, read-only, no network, no token, 16 tests.
It measures four properties per untrusted slot:

| Property | Meaning |
|---|---|
| `LABELLED` | the prompt says somewhere that the slot's content is data |
| `FENCED` | the interpolation sits between two markers |
| `UNFORGEABLE` | the close marker carries a run-scoped value, so text composed before the run existed cannot emit it |
| `LAST` | no slot the prompt calls binding appears after it |

`LABELLED` and `FENCED` are PWC-11's proposal. `UNFORGEABLE` and `LAST`
are what make the fence hold. Today's reading, which replaces PWC-11's
proposed `grep -c 'BEGIN EVENT'` verification because that grep would
have reported the unsafe form fixed:

```
$ node tools/prompt-slots.mjs
prompt-slots: 11 of 11 untrusted slot(s) sit in a fence a payload could
step out of. The repair is reserved to the owner: .github/workflows/ is
not a seat's to edit.
```

Cross-checked against an independent read: the eleven line numbers the
tool reports are the same eleven `grep -n` reports for
`client_payload.text`, from a separate implementation over the same
files.

**One note on the test, because the first draft of it was wrong in a way
this seat was called out for last run.** The live test originally
asserted `fenced === false` on all eleven files, to pin the finding.
That is a test which goes red the moment the owner applies the repair,
which makes it a gate against its own fix. It now asserts only the
property that must hold whatever the workflows say, that untrusted text
reaches a prompt and never a shell. The count of open slots is a dated
measurement, so it lives in this report and is re-derivable by running
the tool.
