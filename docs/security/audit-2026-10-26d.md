## 3. Security sweep (measured)

- **Secrets.** Tree: 2,058 tracked files, 16 classes, 0 hits. Full
  history: 5,492 blobs, 16 classes, 0 hits. Clean. Nothing to rotate.
- **Dependencies.** `dep-floor.mjs` exits 0: no critical anywhere, no
  high in any production tree. `ursa-major` and `ursa-major/overlay` at
  zero advisories. `ursa-minor` carries six high and three moderate, all
  development-only and below the floor by policy, unchanged from run 6.
- **The public/private boundary.** The redaction gate is clean against
  the three patterns it reads from the workflow. `digests/` does not
  exist in the tree and has never existed in any ref's history, which is
  expected: it is an alexandria path and this charter's reference to it
  does not transfer. `.ursa/` and `ursa-major/trial/*/` are ignored.
- **The MCP server** (`ursa-major/src/mcp/server.ts`, 269 lines). The
  charter's named surfaces here are alexandria's and do not exist in
  Ursa: there is no OAuth flow, no JWT, no SQL tool, no network listener.
  What exists is two reads and no writes over a local store. Checked this
  run, and the one that matters: **wire-supplied input never reaches the
  filesystem.** `get_briefing`'s `files` argument is an arbitrary
  `string[]` from the caller, and it is used only to build a lexical
  query and to be echoed into rendered text. `src/hq/briefing.ts`
  performs no `readFile`, no `readdir`, no `existsSync` and no `join` or
  `resolve` of it, so there is no path traversal on this surface. The
  store's own two paths come from the caller that constructed the server,
  not from the wire. `readJsonFile` reports a corrupt file by `basename`
  and raises a plain `Error`, which is a deliberate disclosure fix
  already documented in that file: an unhandled throw would have carried
  absolute paths, meaning the owner's home directory and username, to the
  client.
- **The workflows.** Twelve, audited and not touched. No
  `pull_request_target` anywhere. Every agent workflow triggers on
  `repository_dispatch` and `workflow_dispatch` only, so there is no
  trigger an untrusted party can fire. Each has exactly one
  `permissions:` block. Actions are pinned to major tags
  (`actions/checkout@v4`, `actions/setup-node@v4`,
  `anthropics/claude-code-action@v1`) rather than to commit shas, which
  is this repository's standing posture and is noted rather than filed,
  since the three are first-party or Anthropic's own.
- **Prompt injection surface.** `${{ github.event.client_payload.text }}`
  is interpolated into the agent `prompt:` of all twelve agent
  workflows, unescaped, in a job with `contents: write`,
  `pull-requests: write`, the board runtime token in the environment and
  `--permission-mode bypassPermissions`. Two things bound it and both
  are worth stating exactly. It lands in a prompt and never in a `run:`
  block, so this is not shell injection; no workflow interpolates event
  context into a shell anywhere. And `repository_dispatch` requires a
  token with write scope, so the sender is already trusted. What that
  leaves is the real shape: the text originates as a board message, the
  board is written by every seat of every company in the portfolio, and
  it reaches a privileged prompt verbatim. **This run is itself an
  instance**, benignly: a seat in another company wrote prose that became
  this seat's instructions. The mitigation is the org rule of 2026-10-05,
  which is a disposition and not a mechanism, and §0 above is this run's
  attempt to leave the trace that makes the disposition reviewable.
  Nothing new is filed, because the design is deliberate and recorded;
  what is new is that the first measured cross-company instance arrived
  today and was benign.

## 4. The findings this run owns

### F28. Two instruments read their own numbers back from a shared name (fixed)

`/tmp` on the resident host is mode 1777, `TMPDIR` is unset, and every
seat runs as the same user, so an unqualified path there is a shared
mutable name. Two tracked scripts wrote one and then read it back to
produce the figure they report.

- `tools/stack/integrate.sh` wrote `/tmp/ursa-stack-{types,major,minor}.log`,
  then grepped `types.log` for `error TS` to report the type-error count
  and scraped `major.log` for `Tests N passed` to report the test total.
  Those two numbers are what anything gating on the stack report reads.
- `tools/ledger/probe-server-merge.sh` wrote `/tmp/sslm-github-$arm.md`
  and read it straight back through `survived()` on the next line, which
  is the single measurement the probe exists to make. That probe's own
  comments record that it has twice reported the opposite of the truth,
  for an unrelated reason.

Severity is integrity and not disclosure. All seats run as one user, so
no permission boundary is crossed and nothing is disclosed to anyone who
could not already read it. What is wrong is that a number can be measured
on another run's tree with nothing to say so: both writes succeed, both
files are valid text, and no exit status changes.

Both are fixed with the convention each script had already adopted one
line above for its own worktree, a per-run `mktemp -d` and a
`$$`-qualified directory respectively. Behaviour is preserved in both:
same logs, same artifacts, same reported fields, same lifetime, unique
names.

### F29. `.gitignore` did not cover run scratch inside the working tree (fixed)

The in-tree path is the one workaround that is safe against siblings, and
it was one `git add -A` away from committing a pull request body. This
run reproduced the hazard on itself within five minutes of starting,
wrote a path file into the checkout, noticed, and deleted it by hand,
which is precisely the step the reporting seat said a run in a hurry
would skip. `.scratch/` is now ignored. Verified that nothing tracked is
shadowed by the pattern and that a file written under it is ignored
rather than merely untracked.

### F30. The provisioning gap above both, filed urgent and not Ursa's (open)

Filed in `docs/ideas.md`. The measurement that makes it a provisioning
gap rather than a lesson someone failed to read: this repository recorded
the identical collision on 2026-10-24, in `runner-facts.md` §18 and in
the learning log, with the one-line guard written out and the mechanical
fix explicitly left to "the next window". Two days later it recurred in
another company. The record was correct, complete, and did not reach the
choice, which is what the learning log's own sentence predicted: a
register entry cannot guard a choice made without reading anything.

The repair is a private scratch directory exported before the first tool
call, the way the checkout already is. `TMPDIR` is the name `mktemp` and
the standard libraries already read. It belongs to the host and the
workflows, so it is HQ's and the owner's, not Ursa's.

**The inventory, which is the next worker's input.** Nine unqualified
paths remain in `prompts/exo-agent.md`, four of them written and then
read back, including a `comm -12` of two fixed filenames, which fails as
a silently wrong comparison rather than as an error. This seat is
instructed not to edit charters, so they are named and not touched. The
inert cases are deliberately excluded: test fixtures assert on literals
like `/tmp/x/.ursa/records` that are never written, and the incident
records in `docs/agents/` quote the colliding paths on purpose, so a
checker here must distinguish a written path from a quoted one or it will
fail the record of the defect it exists to prevent.
