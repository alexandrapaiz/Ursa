this run used.

## 3. F41 — a green gate after a red one is not a remediation. New, and fixed here.

**Severity: medium as a documentation defect, and it is the reason an
existing urgent finding is scoped too narrowly.**

`docs/security/redaction-standard.md` is thorough about the gate's
detection limits. It says the gate reads the working tree and not
history, that its allowance is line-scoped, that it is blind to Class A,
and that passing it is "the backstop firing early". It then gives a
recovery procedure for a missing verdict. What it never says is what a
*red* run has already cost.

The gate fires on `pull_request`. By that point the commit is pushed and
`refs/pull/<n>/head` exists and points at it. That ref survives a force
push, a history rewrite, a branch deletion, and the closing or merging of
the pull request. So the sequence a seat reads as a save, red gate, fix
the line, push, green gate, does not reduce the exposure at all. It only
stops the gate from reporting it.

**Why this is a finding and not a restatement.** Three seats have now
touched one face of this each. The skill seat found that the dirty commit
stays a strict ancestor of its own green branch. Run 16's F38 found
incident 2's purged records fetchable by ref name. Run 16's ledger entry
states the generalisation correctly. None of that reached the file a seat
actually reads when the gate goes red, and the fix for the instance is
written there, two sections above, with no warning attached. A procedure
that produces the appearance of remediation, in a document that is
otherwise careful about this gate's limits, is the merged-documentation
defect class this charter names first.

**It also rescopes F38.** F38 asked the owner for a GitHub Support
request covering `refs/pull/1` and `refs/pull/2`. Every leak this gate
has ever caught on a pushed branch is in the same position and needs the
same remedy. The owner's decision on F38 is therefore a decision about a
larger set than F38 described. That does not change the action, and it
changes what the action is worth.

**Measured instance, live while this was written.** PR #570 on
`ursa-frontend/2026-10-27-hook`, open and not a draft, turned
`redaction-gate` red eight times between 00:28 and 00:50 UTC on one
Class A identifier at `docs/design/review-kit/state/panel-payload.mjs:53`.
One commit reachable from `refs/pull/570/head` carries the value in full.
Verified by walking the pull ref's commits and testing each tree for the
class, counting matches only. The value is not quoted here, in the
standard, or in any commit message on this branch.

**The prediction was then watched happening, which is why F41 is
CONFIRMED rather than argued.** At 00:55 and 00:59 UTC that branch's gate
went green, because the seat fixed the line, which is correct and is what
the standard asks for. Re-measured against `refs/pull/570/head` at
00:59Z: the tip tree is clean, the gate is green, and the dirty commit is
still reachable with the count unchanged at one. Red, fix, green, and the
exposure did not move. This is the finding as an observation rather than
an inference, made on a live branch inside this run's own window.

**Not routed as new work to the frontend seat.** The engineer seat handed
this leak to frontend by name at 00:40Z with the file and line, so the
instance is already in front of the seat that owns the file, and the file
is not this seat's to edit. What this run adds is the part that handoff
could not contain, which is that fixing the line does not close the
exposure. That now lives in the standard.

**Fixed here:** a new closing section of
`docs/security/redaction-standard.md` stating the mechanism, naming the
two obligations it creates for a seat, and recording the measured
instance.

## 6. The ExO seat's correction, verified rather than accepted

The ExO seat told this seat on 2026-10-26 that the ship-first draft sweep
matches a narrower branch pattern than the section that finds the same
branches, and that it had queued the one-line repair on its charter
branch. It then sent a correction saying the second half was false and
the edit had been on no branch.

Both the finding and the correction check out, read at the ref:

- `prompts/security-agent.md` on `main` line 64 tells this seat to open
  on a `sec/YYYY-MM-DD` branch. Line 93 matches `test("sec|security")`.
  Line 219, the ship-first sweep, matches `test("security")` only. So a
  `sec/` branch, the form this charter itself prescribes, is visible to
  the first and invisible to the second, and the sweep then prints
  nothing, which is what it also prints when there are no dead drafts.
- The repair now genuinely exists. `git diff main...refs/pull/571/head --
  prompts/security-agent.md` shows the widening to `test("sec|security")`
  plus the rule that the two patterns must agree. #571 is open and not a
  draft, so it is waiting on the owner, which is correct for a `prompts/`
  path.

**It did not bite this run, and that does not reduce it.** This run's
branches are all `ursa-security/…`, which contains `security`, so the
narrow pattern would have found them. The blind spot is specific to the
`sec/` form, and the charter prescribes the `sec/` form, so the next run
dispatched onto one inherits the defect. A charter is outside this seat's
write surface, so the corroboration is the whole of this seat's action.

**On the false claim itself.** The ExO seat's reason for correcting it is
right, and it is a reusable one: a claim that a repair is already queued
is the single statement most likely to make the seat holding the defect
stop looking at it. This run verified the second claim at the ref before
relying on it, for that reason.
