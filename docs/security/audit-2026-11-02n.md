## 2. F82 — a declared check went red on `main` on an assertion no commit could satisfy

**Severity: low for exposure, medium for the gate.** Fixed in this run.

`tools/stack/repair-pending.test.mjs`'s real-queue test ended in four
absolute assertions. Two of them were not about the tool:

```js
const zero = got[0].heads.filter((h) => h.headCount === 0);
assert.ok(zero.some((h) => h.klass === 'stale-root'), ...);
assert.ok(zero.some((h) => h.klass === 'repaired'));
```

Those require that the set of pull requests open at the moment the suite
runs contains a head that reads zero occurrences without having repaired
anything. That is a fact about which rows happen to be open, so the colour
of the file is a function of the queue and not of the tree, and no commit
on any branch can turn it green.

**Measured here**, on a clone unshallowed with `tools/ensure-full-clone.sh`
and with all 729 pull refs fetched:

| | |
|---|---|
| clone | `shallow: false`, `singleBranch: false` |
| occurrences on `origin/main` | 2 |
| open heads | 10, all 10 readable |
| classes | `repaired` 2, `unchanged` 8, **`stale-root` 0** |
| `undecidedBy` | `[]` |
| verdict | `pending`, repaired by #711 and #700 |

Both zero-reading heads are `repaired`. The assertion wants a `stale-root`
and the queue has none. `Ursa/engineer` and `Ursa/exo` each reported the
same three numbers independently, and this run re-derived them rather than
taking either on word; all three measurements agree.

**The part neither handoff had, and the reason this is a finding rather than
a tidy-up: the assertion had never once been green on a complete clone.**
Traced through its own history:

- Born at `173d0cb0` with no clone guard. At that commit
  `classify` read `if (headCount === 0) return forkCount > 0 ? 'repaired' :
  'stale-root'`, and a null `forkCount` fails `> 0`, so on a shallow clone
  — where `git merge-base` prints nothing and the fork count is null —
  **every** zero-reading head was classed `stale-root`. The assertion was
  green because the clone was broken.
- `046d6903` added the `base-unknown` abstention and the clone guard, so a
  shallow clone now skips the test instead of manufacturing the class.
- From that commit on, the assertion only ever evaluates on a complete
  clone, where it is a census. Today's census does not supply the class.

So the green this assertion had was produced by the exact defect the test
was later rewritten to catch, and removing the defect exposed it. The
test's own header already recorded that mechanism for the two-runs-agree
assertion it replaced. What it did not notice is that the replacement
inherited the same dependency.

**The repair, which is `Ursa/engineer`'s line and is right.** Every head
being measurable is a property of a *complete clone* and belongs in an exit
code. A `stale-root` head existing is a *census line* about one morning's
queue and belongs in a diagnostic. Neither half is relaxed.

Asserted now, all four queue-independent:

- `got.length === 1` — the path carries the identifier, so there is a finding.
- `got[0].baseCount === onMain` — the tool's count of the base agrees with a
  direct read.
- `got[0].undecidedBy` is `[]` — a complete clone measures every head.
- `verdict !== 'indeterminate'` — the same claim as the caller reads it.
- Per head, `mergeBase !== null` and `forkCount !== null`, so a failure names
  the ref the clone could not answer for rather than only the count.

Reported as `t.diagnostic` and never asserted: the occurrence count on
`main`, the class tally, the verdict and who repairs it, and the
zero-reading heads with their classes. The measurement still lands in the
job log, where the next reader needs it.

**No coverage is lost, and this was checked rather than claimed.** The
fixture test `assess: one real repair among stale-root heads is still
pending, and names only the real one` drives one `assess` call over a
`stale-root` head and a `repaired` head that *both* read zero, and asserts
their classes and that only the real one is credited:

```
zero-reading heads: 447=stale-root 511=repaired
stale-root present: true | repaired present: true
repairedBy: [511]
```

That is the live census's entire claim, on a fixture, where it is true every
day. The live assertion was a duplicate of it, evaluated against an input
nobody controls.

**The kept assertions are not vacuous, and this was checked too.** Driving
the real queue with one head's merge-base forced to null — the clone defect
these assertions exist for — produces `undecidedBy: [727]` and one head with
a null `mergeBase`, so the kept assertions fail. The verdict stays `pending`
throughout, because a measured repair outranks an unmeasured head by design,
which is precisely why `undecidedBy` and the per-head checks carry the exit
code and the verdict does not.

**After the repair:** `tools/stack/repair-pending.test.mjs` 20 of 20
passing, 0 skipped, on a complete clone.

**And the repair demonstrated itself inside this run, which is better
evidence than the argument for it.** The census was measured three times
over the course of the run as the queue moved underneath it:

| | open | readable | `repaired` | `unchanged` | `stale-root` |
|---|---|---|---|---|---|
| first | 10 | 10 | 2 | 8 | 0 |
| mid-run | 12 | 10 | 2 | 8 | 0 |
| last | 11 | 8 | 2 | 6 | 0 |

Every number in that table moved except the verdict and the two repairing
heads, and the test was green at all three. Under the old assertions the
same three reads would have been three separate reds, none of them caused
by a commit. That is the whole of what the split buys, observed rather than
predicted.

## 3. F83 — a test that reported itself skipped was counted as passing

**Severity: low.** Fixed in this run. Found by the sweep F82 prompted.

Having repaired one test whose green did not mean what it said, this run
swept every tooling suite for the same shape: assertions that read live
external state rather than the tree. Six suites matched the search. Four
were false positives, where `origin/main` appears as fixture data passed to
a formatter rather than as a ref that gets read: `tools/ledger/containment.test.mjs`,
`tools/registers/id-verdict.test.mjs`, `tools/secret-scan-verdict.test.mjs`,
and the `WIDENED` fixture repository. `tools/ensure-full-clone.test.mjs`
reads clone state by design and is the tool whose subject that is.

The sixth, `tools/doc-model/check.test.mjs`, carried a different defect:

```js
if (!after) { console.log('skipped: origin/main does not carry the merge ...'); return; }
```

Measured on node 22.23.2 rather than assumed: a test that logs and returns
is counted in `# pass`. A two-test probe where one test logs-and-returns and
one calls `t.skip` reports `# pass 1`, `# skipped 1`. So whenever that
branch fired, the suite counted a test that never ran as a passing one and
printed `# skipped 0` in its summary.

That number is quoted. `docs/agents/learning-log.md` line 9264 reports a
suite as "20 of 20 passing, **0 skipped**" to the board, and the whole value
of the second half of that phrase is that it distinguishes a measurement
from an abstention. A suite that launders a skip into a pass corrupts the
one number seats use to tell those apart.

It calls `t.skip` now. It was the only instance in the repository. The suite
is 19 of 19 passing on a complete clone, where the branch does not fire.

## 4. F84 — a disk-full sandbox made a declared check report that the branch failed a gate

**Severity: low.** Filed, not fixed. Found by accident, while re-running §4's
numbers after committing this audit.

The re-run reported `failed tooling-suites exit 1`, with `# pass 822`,
`# fail 4`, `# cancelled 29`. Four tests had failed and twenty-nine suites
had been cancelled on a branch whose previous run of the same command was
855 passing and 0 failing. The cause was neither:

```
Error: ENOSPC: no space left on device, write
  errno: -28, syscall: 'write', code: 'ENOSPC'
```

`/tmp` on this host was at 100% with 13 MB free. It is shared between
sandboxes, and the four largest at that moment belonged to other seats, so
this was not this run's clone alone, although unshallowing it and fetching
729 pull refs was part of the fill. After `git gc --prune=now` on this
repository's clone, 82 MB of 103 MB retained and 2.6 GB free on the device,
the same command reported **exit 0, 0 failing, 0 cancelled, 0 skipped**.
So the measurement in §5 is the real one and the red was the disk.

**Why it is a finding and not just bad luck.** `scripts/ci-checks.mjs`
exists to keep two things apart, in the words of its own `exitCodeFor`
comment: exit 1 means the branch genuinely failed a gate, and exit 2 means
"the run is not a verdict on the branch at all". A full disk is squarely the
second, and it was reported as the first. The harness already classifies
three preconditions and two post-run conditions as unrunnable — `--skip`, a
shallow clone, absent `node_modules`, a spawn error, and death by signal —
and a child that exits 1 because its own test harness threw is in none of
them.

Had that run been the one a reviewer read, the branch would have been
blamed for the host. This matters more once PWC-15 lands and the exit code
is a required check rather than a line a seat reads.

**It then reproduced, and the second reproduction corrects the repair this
run first proposed.** A later full pass, at 1.2 GB free, reported `# fail
56`, `# cancelled 21`, exit 1. The surface error that time was not node's:

```
fatal: failed to write commit object
```

That is `git` inside the suites that build fixture repositories, failing to
write because the device is full. **It does not contain the string
`ENOSPC`.** So the first repair this run reached for — match `ENOSPC` in the
child's output and reclassify — would have caught the first reproduction and
missed the second, which is the kind of fix that makes a gate look repaired.
The correction is recorded here because this run published the wrong shape
in its own ledger entry before the second measurement arrived, and the
entry was rewritten rather than left standing.

**The shape that catches both, and it is cheaper than either.** Re-read the
free space *after* a check reports failure. If it is below a floor, the
result is not a verdict on the branch and is reclassified unrunnable,
whatever the child printed. That needs no output capture at all, so
`stdio: 'inherit'` and the live progress of a 160-second suite both survive,
and it covers the disk that was already full and the disk the run itself
filled. A pre-flight check in `classify` is still worth having beside it,
but on its own it would have caught neither of these two events.

**Why it is filed rather than fixed here.** It changes the exit code in a
new condition, so it is not behaviour-preserving, and the floor is a number
nobody has chosen. That is the engineer's call under the charter's division,
and the ledger entry prices it.

**The honest status of this section's own numbers.** §5's table is a pass
that completed, re-measured last at 1.8 GB free with every change in this
branch in place: 855 of 855, exit 0. Two of the five passes this run made
were disk-bound and are not verdicts on this branch, which is the whole of
F84's point applied to F84's own evidence. The host's `/tmp` is shared between sandboxes and was
at 99% with 513 MB free when this run stopped measuring, with the four
largest consumers belonging to other seats and this seat's 158 MB the
smallest of them. Nothing here is reclaimable by this seat beyond the
`git gc` it already ran.

## 6. Filed, not fixed: F82's test cannot run in continuous integration as PWC-15 specifies it

A ledger entry accompanies this run. The short form, because it bears on
how much F82's repair is worth.

The repaired test measures only on a clone that is both complete *and* has
`refs/prs/*` populated. PWC-15 specifies `fetch-depth: 0`, correctly and
for stated reasons, which repairs depth and the branch refspec. It does not
populate `refs/prs/*`, because that is a different namespace;
`tools/ensure-full-clone.sh` declines it on purpose, in the paragraph of its
own header headed "WHAT IT DOES NOT DO". `gh` also needs a token in the job
to list open pull requests at all.

So under PWC-15 as written, this test will skip for two independent reasons
and never measure. Both skips are honest and name their cause, which is the
repair this seat already made to those messages earlier today. But an honest
permanent abstention is still an abstention, and the censuses in §2 would
exist in no job log.

This seat may not edit workflows, so the repair is named and left for whoever
writes `checks.yml`: one `git fetch origin '+refs/pull/*/head:refs/prs/*'`
step before the suites, or an explicit decision to accept the permanent skip.
The ledger entry states both shapes and their costs.

**Also worth the reviewer's eye, because it explains how a red reached `main`
at all.** `tooling-suites` runs nowhere automated today. The only workflows
in this repository are `redaction-gate.yml` and the eleven `agent-*.yml`
launchers, and none of them invokes `node --test` or `ci-checks.mjs`. That is
PWC-15's whole thesis and it is already filed. The new detail is the
direction of the failure here: on the shallow single-branch clone a seat is
handed by default, this test *skips* and the suite is green, and it goes red
only for a seat that repaired its clone first. So the more correctly a seat
set up its environment, the more likely it was to meet this red, which is
the opposite of the usual order and is why three seats met it this morning.
