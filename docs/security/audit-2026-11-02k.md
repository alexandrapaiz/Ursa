## 2. F73 — PWC-15's prescribed job runs none of the product's tests, and goes green doing it

**Severity: high.** This is the finding this run exists for. It is not an
objection to PWC-15. That entry should be applied; the thesis is correct and
the window it measured was real. The finding is that the job it prescribes
does not do what the board item above it promises, and that it will report
success while not doing it.

**What the board item promises.** "Every test and gate we have built runs
before a change can reach the default branch."

**What PWC-15 prescribes for the test half,** verbatim, as the step named
`Unit suites`:

```
node --test $(find . -name '*.test.mjs' -not -path './.git/*' -not -path '*/node_modules/*' | sort)
```

**What that command reaches, measured on this tree.** 47 suites, all of them
tooling under `tools/` and `scripts/`, carrying 811 `test(`/`it(` calls.

**What it does not reach.** `ursa-major`, which is the product. `ursa run` is
the only thing this company has shipped (M0, per `CLAUDE.md` §0). Its tests
are 52 suites in `ursa-major/src/**/*.test.ts` carrying 874 cases, and its
`npm test` is `tsc --noEmit && vitest run`. The glob `*.test.mjs` does not
match `.test.ts`, `node --test` is not the runner, and the typecheck is a
separate instrument again. Also unreached: `ursa-minor`'s `next build`, its
`eslint`, and its three `check:*` scripts.

So the step covers 811 of 1,685 test cases in this repository, and the 874 it
omits are the ones that protect the shipped product. A branch that breaks
`ursa run`, or that does not typecheck, passes.

**Why nobody has caught this, and why it is worse than a broken step.** The
47 suites the command does reach import nothing outside the Node standard
library, which was checked rather than assumed: every bare specifier across
all 47 is a `node:` builtin. So on a fresh runner, with no dependency install
step anywhere in the prescribed job, that command runs and goes green. The
job is not broken. It is silently partial, and it is partial along exactly
the line that a dependency install would have made visible — the product's
suites import `vitest`, `jsdom` and `@modelcontextprotocol/sdk`, and would
have failed loudly on a runner with no `node_modules`. The half that needs no
setup is the half that got specified.

A check that passes while covering half the repository is the board item's own
thesis one layer in. The item says a gate that is not in continuous
integration does not fail late, it fails invisibly. A gate that is in
continuous integration and silently covers half of what its title claims
fails invisibly too, and it is harder to notice, because now there is a green
tick next to it.

**Confirmed that nothing else picks up the slack.** `grep` over `.github/`
for `npm ci`, `npm test`, `npm run`, `vitest`, `tsc --noEmit`, `next build`,
`eslint` and the three `ursa-minor` check script names returns zero hits. The
product's tests are run by nothing in this repository except a seat session
that remembers to.

## 5. F76 — `main` was red in three tests, and the entry above is why nobody knew

**Severity: medium, and already fixed in this run.** Found by running
PWC-15's own prescribed step rather than by reasoning about it, which is the
only reason it was found at all.

Three failures on clean `origin/main`, reproduced in a separate worktree
checked out at `origin/main` so that none of them could be attributed to this
branch or to the #709 merge underneath it:

| suite | test | cause |
|---|---|---|
| `tools/doc-model/check.test.mjs` | the shipped registry has no errors for the seat that owns the files it can fix | asserted `candidates === sites` |
| `tools/ledger/block-kinds.test.mjs` | every real heading that announces a scan is classified as one | asserted classification purity |
| `tools/ledger/block-kinds.test.mjs` | the real file has exactly one tag-announced scan, and it is the one measured | pinned to a block in an unmerged branch |

All three suites arrived on `main` in #704, merged earlier today, and all
three were red from the hour they landed. This is the board item's thesis
demonstrated a second time on the same day: the item cites a malformed block
that reached `main` at 01:44Z under an all-green merge, and these three have
been red since, under green merges, with no instrument looking.

**The first one, and why the gate was right and the test was wrong.** Probe
finds 16 candidate sites against 14 registered. The two unregistered ones are
both in `docs/agents/runner-facts.md`, which belongs to the `exo` seat. The
gate is built for exactly this case: `mineToEdit` downgrades both
`UNREGISTERED_SITE` findings from `error` to `warn` and routes them to the
owning seat by mail instead of through an exit code. The test's first
assertion honours that and passes. Its second compared the raw counts and so
went red on prose that no seat reading the failure was permitted to edit.
PWC-15 names this shape itself, about the ledger gate's exit 2: a check that
no branch can turn green is one every seat learns to ignore. Repaired to
assert what the gate actually guarantees, which is the property worth having:
every candidate is accounted for, each unregistered one produces exactly one
finding, and each finding names the seat it routes to.

**The second, where the module is right and the test over-reached.** The
block is the engineer's `Craft scan: doctest and Rust's #[doc] tests`. It
carries a `- First step:` line, so `COMMITS_WORK` classifies it as an idea
rather than a scan. That rule is literal by design and `block-kinds.mjs`
argues for it at length, including refusing the alternative of reading the
sentence after the label. The rule is not wrong here. What does not fit is
the repair the test's failure message recommends, which is written for a scan
note with *nothing* to propose and tells the author to say so in prose. This
note has something to propose, states it concretely, and carries all five of
§4's fields. `node tools/ledger/check.mjs` reports nothing against it. So the
harm the assertion names, "owes §4's five fields and will go red", cannot
occur for this block. Repaired to assert the property instead: a
scan-announcing block must be either a `scan` or a complete idea. Checked
that this still catches the original defect, by deleting the `Cost` field
from that block and confirming the test goes red, then restoring it.

**The third, which is L-E10 from the other end.** The test asserts exactly
one tag-announced scan and names the heading `### 2026-11-02 (engineer, craft
scan) — ...`. That block is not in `docs/ideas.md`. It is in pull request
#665, which is open and unmerged, confirmed by diffing all four of the
engineer's open pull requests. So the test was written against a working tree
that carried #665's content and then merged onto one that does not, and it
goes red on every branch for as long as #665 stays open. The org rule in
every charter says `main` is not this organization's memory and a seat's own
work may be sitting in its open pull request. This is the inverse and it is
worth naming separately: a *test* may be pinned to content sitting in
somebody else's open pull request, and then it is everybody's red. The
comment above the assertion states its purpose as an upper bound, that the
rule must reclassify no more than one block and a second is a reason to
re-read the rule. That bound is kept exactly. The lower bound was a
measurement of the author's working tree rather than a property of the rule,
and it is now conditional, so the identity check starts running again by
itself when #665 merges.

**The property it holds, which is the one F73 found missing.** A declared
check that cannot be run is reported `unrunnable` and the run exits 2. Never
a silent skip, never a pass. Exit 0 means every declared check ran and
passed, 1 means one ran and failed, 2 means the run is not a verdict on the
branch at all. Skipping is possible but only by naming the check on the
command line, which leaves the omission in the job log.

**Verified end to end on this tree, not asserted.** `node
scripts/ci-checks.mjs`, full run:


- Both product checks report `unrunnable` with the command to fix it, because
