## 2. F79 — a tracked binary that is not an image was read by nothing, and reported clean by this seat's own gate

Severity medium. Owner: this seat. **Fixed in this run.**

### What the board item asked for, and what was actually missing

The item in the In progress column is about images in the redaction gate. That
half is covered and was covered before this run: `tools/image-metadata.mjs`
parses every tracked PNG and the one ICO at the container level and refuses any
chunk that can hold text. PWC-13 carries the other half, dropping `grep -I`
from HQ's workflow, and it is still HQ's.

PWC-13's own closing paragraph names what remains after that flag lands:

> it reaches **text sitting in a binary file that is not an image at all** — a
> font, an archive, a compiled artifact — which nothing in this repository
> looks at today.

That sentence is true about reading. This run found it is also true about
reporting, which is the worse half, and that the worse half is in this seat's
own lane rather than HQ's.

### Measured, not inferred

`tools/image-metadata.mjs` selected its input with an extension list,
`IMAGE_EXT`. A tracked file that is binary and matches nothing in that list was
not refused by the gate. It was never enumerated. Against a throwaway
repository holding one PNG and one `.woff2` carrying a fabricated home path in
an ASCII run between NUL bytes:

| checker | sees the carrier? |
|---|---|
| `tools/image-metadata.mjs` | **no** — exits 0, reports `images: 1` over two binary files |
| the gate as it ships, `/usr/bin/grep -rInE` | **no** — `-I` suppresses it, exit 1, nothing on either stream |
| the same with `-I` dropped, which is PWC-13 part 1 | yes — `binary file matches` on **stderr** |
| `tools/secret-scan.mjs` | credential classes only, not the redaction classes |

So the gate printed a clean line and a count, and the count was one over a tree
of two binaries. A clean report over a file nobody read is the exact failure
`scripts/redaction-check.mjs` was written to refuse, and it was sitting in the
gate next to it.

Measured with `/usr/bin/grep`, GNU grep 3.11, never a shell `grep`, for the
reason PWC-13 records at length: the shell `grep` in this runtime is a harness
function that inserts `-I` ahead of the caller's arguments, so a seat that
removes `-I` deliberately still gets it and reads a carrier as a clean tree.

### What was changed, and what deliberately was not

The enumerator, not the reach. The gate now lists every tracked binary, decided
by a NUL byte in the leading 8,000 bytes, which is the test git itself applies
and the test that makes GNU grep call a file binary and skip it under `-I`. One
definition rather than a second one that could drift from the gate's.

Anything in that set the gate cannot parse is a new ground cause,
`BINARY_UNREAD`, at exit 2, whose message names both repairs: parse it here, or
land PWC-13. The image walk still runs first, so an image in an unparsed format
keeps the sharper `FORMAT_UNPARSED` diagnosis that names the reader it needs.

**This changes no exit code on this tree, and that is the point of stating the
census.** All 1,333 tracked binaries are the 1,332 PNG and one ICO the gate
already parses, measured independently of the gate with `/usr/bin/grep -lI`
over `git ls-files`. The gate was correct about this repository today. It was
silent about the category, and silence is what a gate cannot be.

**What this does not buy.** A ground fault says nobody looked. It does not
look. The gate still cannot tell whether such a file holds a home path, and the
only thing that can read one is the `grep` in HQ's workflow with `-I` off. The
question can no longer be missed, which is the half a seat can hold in its own
lane. PWC-13 is updated to say exactly this, so nobody reads the entry as
closed.

### Why the equality is asserted and not commented

`seen.images` is now a coverage claim rather than only a count, and that
property rests on the binary set and the parsed set being equal. A comment
saying so would be true on the day it was written.
`tools/image-metadata.test.mjs` asserts `unreadBinaries('.')` is empty against
the real tree, so the day a font or an archive is committed, the suite says so
and not only the gate.

Seven new assertions in all, including the two shapes that have to produce exit
2 rather than a clean zero, the ordering property that keeps `FORMAT_UNPARSED`
reachable, and a text file named `.woff2`, which is left alone because the
redaction gate's patterns already read it.

### One thing this run got wrong and the gate caught

The first version of the test fixture carried a plausible `/Users/<name>/`
string to make the binary carrier realistic. `scripts/redaction-check.mjs` went
red on the test file itself. The fixture now uses the standard's own
placeholder form, which is enough, because the NUL is what makes the file
binary and binary is all these tests assert.

Recorded rather than quietly fixed, for two reasons. It is evidence the
redaction checker works on a file added in the same run that added the checker's
own subject. And a security suite that trips the redaction gate in order to
demonstrate the redaction gate is not a fixture, which is a thing worth having
written down where the next run will read it.

## 3. F80 — the finding-identifier namespace is unregistered, has two undocumented numbering schemes, and carries three unrepaired collisions on `main`

Severity low in isolation, and it degrades every cross-reference this seat
makes. Owner: this seat for the registration, the owner for the three merged
collisions. **One collision repaired here, three reported, the gate filed.**

### How this was found, and the first reading was too narrow

Found by reading this seat's own open pull requests, which the charter puts
first. #722 files a finding as F74, and `audit-2026-11-02k.md` §3 is a
different finding already carrying F74 on `main`.

The first reading of this run was that two concurrent runs had collided once
and could not have seen each other. Both halves of that turned out to be wrong,
and the correction is the finding. **Withdrawn here rather than left standing:**
`tools/registers/check-ids.mjs` has a `--heads` mode that fetches every open
pull request head and an allocator, `--next <NS> --heads`, so a run could have
seen the other branch's allocation at the moment it allocated. This seat built
that tool. The collision is not a limit of what was knowable.

### The tool already refuses to do the thing that caused this

Run in this sandbox, which is the evidence rather than a reading of the source:

```
node tools/registers/check-ids.mjs --next PWC --no-fetch --base HEAD
-> NEXT_WITHOUT_HEADS: an allocator that reads one branch is how PWC-7
   came to mean two changes at once; re-run with `--heads`.   exit 2

node tools/registers/check-ids.mjs --next PWC --heads
-> PWC-16
   computed from 15 identifier(s) defined or burned across 11 ref(s)
```

So the allocator refuses to answer from a single branch, and its refusal names
the exact failure this finding is about. Across eleven refs it then answers
correctly. Had `F` been a registered namespace, `--next F --heads` would have
returned the next free number and none of the four collisions below could have
been allocated.

That is the whole of F80 in one line: this seat built a gate against
identifier collisions, wrote a refusal into it so nobody could allocate blindly,
registered four namespaces in it, and left out the only one it allocates
itself.

### What the registry says, and what is not in it

`tools/registers/id-namespaces.json` declares four namespaces: `ADR`, `PWC`,
`PWC-ENG`, `PWC-EXO`. Its own comment reasons explicitly about what it leaves
out and why, excluding `L-A`/`L-E` as HQ's and `INC-` as content-derived, and
states the principle plainly:

> A namespace with no `why` is a fault, not a default.

`F` is not in the file, and it is not in the list of deliberate exclusions
either. So the one namespace this seat allocates for itself, in its own audit
reports, is the one namespace absent from its own collision gate, with no
recorded reason. That is the finding, and it is sharper than a collision,
because `PWC-7`'s own burn note in that file reads "which is the collision this
gate exists for".

### Measured across every audit, which is where it stopped being one collision

Every `F<n>` definition in `docs/security/audit-*.md`, parsed from headings:

```
distinct F identifiers defined                70
identifiers defined more than once            14
```

Those fourteen are two different things, and separating them is the point:

**Eleven are not collisions. They are a second numbering scheme.** Four early
audits numbered their findings locally from 1: `audit-2026-10-04.md` F1–F11,
`audit-2026-10-17.md` F1–F7, `audit-2026-10-25.md` F1–F11,
`audit-2026-10-27.md` F1–F3. From `audit-2026-10-26.md` at F12 onward the
numbering is global and monotonic. Both schemes use the same prefix and neither
is written down anywhere, so `F3` does not resolve to a finding at all, it
resolves to four of them, and a reader cannot tell from the citation which
scheme the citer meant. This run read `F73` and `F74` as global because the
recent audits are, which happens to be right and was not checked at the time.

**Three are genuine collisions in the global scheme, and they are on `main`
now.** `audit-2026-11-02g.md` and `audit-2026-11-02h.md` both define F64, F65
and F66, as six different findings under three names. Both files are merged.
Two of the six are worth naming for how badly the ambiguity reads: g's F64 is
"two declared windows the board had outgrown" and h's F64 is "the evidence that
called F59 latent was an artifact of a dirty clone", so a reference to F64
inside a discussion of F59 resolves to either one.

### What this run repaired and what it deliberately did not

**Repaired: the k/l collision**, because #722 was absorbed into this branch
under the charter's rule about building on top of this seat's open pull
requests, so one tree holds both and the fix is in one place. The merged and
cited number stays with k; run l's becomes F78, with a note in the audit and in
the ledger entry citing it saying it moved and why.

**Not repaired: g and h.** Both are merged and both are cited. Renumbering a
merged, cited finding rewrites what other files already say, which is exactly
the reason `id-namespaces.json` marks `ADR` as `repair: owner` rather than
`repair: seat`. Three numbers across two merged reports is the owner's call,
not a seat's, and doing it quietly inside a run about something else would be
the worst available version of it.

**Not built: the gate**, filed as a `proposed` ledger entry instead, and the
reason is worth stating because it is not only the charter's new-tooling
boundary. Registering `F` today would turn `check-ids.mjs` red on `main` over
the three collisions above and the eleven scheme overlaps, and that red is
correct. It would also block every seat on a repair only the owner can make.
The entry therefore asks for the registration and the heading convention
together, with the scheme split recorded as burned rather than repaired, so
that landing it is one decision with a known cost instead of an immediate
trunk-wide red.

The heading convention is not cosmetic and is the reason this cannot be a
one-line registry addition. A `define` pattern has to be anchored and
unambiguous, and the headings are not: seven distinct shapes appear across the
audits, including `## F<n> — <title>`, `## <k>. F<n> — <title>`,
`### F<n>. <title>`, `## <k>. Finding F<n>: <title>` and `### F<n>(b) — <title>`.
Until one form is chosen, the namespace cannot be parsed, which is the
mechanical reason it was never registered and is a better explanation than
oversight.

## 4. F81 — two register gates existed in the tree and were named in no gate list, so nothing ran them

Severity low. Owner: this seat. **Fixed in this run.**

Found while checking a claim in F80's own ledger entry rather than by a sweep,

That is the board item behind `scripts/ci-checks.mjs` stated one layer in. The

then not running it is that same mistake one layer up. Two more gates were in
that condition, and one of them is the gate against duplicate identifiers,
which sat unrun on the same day this seat allocated a duplicate identifier.

Both are now declared checks. `register-ids` runs single-ref, and the comment
records that as a limit rather than an oversight: `--heads` is the mode that
catches two open branches allocating the same number, and it needs network and
a token, so it belongs on a schedule. The single-ref form catches a collision
in the tree being merged, which is the one a merge can introduce.
`passExit: [0, 2]` follows the reasoning already written for `ledger-contract`
in the same file, since `id-verdict.mjs` exits 1 for a seat-repairable
collision and 2 when the remainder is all the owner's, and `main` carries two
of the owner's today in ADR-005 and ADR-006.

Verified: `--list` reports 11 tooling checks where it reported 9,
`scripts/ci-checks.test.mjs` is 12 pass 0 fail, and both new checks pass.
