## 4. F35 — the scanner's first hit is a fixture, and the rule against it lived in one file's header

**Severity: low as a credential matter, and nothing is to be rotated.
Medium as an instrument matter, which is the whole of it.**

`node tools/secret-scan.mjs --history` returned one hit, class
`aws-access-key-id`, in `tools/secret-scan-verdict.test.mjs` at line 72,
in a blob that exists on one ref: the engineer seat's branch behind the
open draft PR #561. The path does not exist on `main` and does not exist
in this working tree.

**Classified without printing it.** The matched value is the example
access key id that AWS prints in its own documentation. That was
established by comparing the blob against that published string and
counting, rather than by eye, and by reading the surrounding lines with
every key-shaped token masked. The test it sits in asserts that the
scanner's verdict output never contains a credential value, so the
author's intent was the same as this seat's rule. The value is not
quoted in this report, in this pull request, or in any commit message
here, which is the charter's rule regardless of whether a value turns
out to be live.

**Nothing is disclosed and nothing needs rotating.** A value a vendor
publishes in its own documentation is not a credential. The owner has no
action from this finding.

**What it would cost if it merged, which is the actual finding.** This
seat's history scan reports zero, and a zero is the only output that
carries information here. A permanent known hit turns the next real one
into a line in a report that already says one, and turns PWC-14's
proposed gate red on arrival. The predecessor of that failure is already
in this repository's record: a gate that fires on something benign is a
gate seats learn to read past.

**The rule already existed.** `tools/secret-scan.test.mjs` opens by
saying that every canary in it is assembled at runtime from pieces rather
than written as a literal, for two reasons it states plainly, which are
that a committed literal makes the repository permanently dirty by its
own instruments and that a reader skimming a suite should not have to
decide whether a string in it is real. That is the rule the other file
needed. It was in a sibling file's header, which is to say nowhere.

**What shipped here.** Class D of `docs/security/redaction-standard.md`
now carries the rule, the measured instance, and the reason not to
answer this kind of finding by widening an allowance. An allowance makes
the scanner quieter and the repository no cleaner. Assembling the value
costs one line and leaves the scanner able to mean what it says. The
scanner itself is unchanged, deliberately: it did its job, and the thing
that went wrong is upstream of it.

**What is routed.** The file is the engineer seat's and it is not merged,
so the repair belongs to that seat on that branch. It is one line, which
is to build the value from fragments the way the sibling suite does. A
ledger entry carries it and a board message names it, and neither this
report nor this pull request asks the owner for anything on it.

## 5. F37 — the file that promised it never prints the board URL prints it twice

**Severity: low, and latent rather than live.** Nothing was disclosed,
and that was measured rather than assumed.

`tools/board/post.mjs` says in its header that `BOARD_RUNTIME_TOKEN` and
`BOARD_API_URL` are read from the environment and that "this file never
prints either one". The token half is true, and it was checked on every
path: the dry run prints the Authorization header as a placeholder, the
environment faults name the variable rather than its value, and a non-2xx
response prints the board's own body.

The URL half is false in two places. The first has been there since the
file's first commit on 2026-10-26, which prints `POST <url>` under
`--dry-run`, where the URL is built from `BOARD_API_URL`. The second
arrived in #555 yesterday, in the new `BOARD_URL_SCHEMELESS` fault, which
names the unusable value on purpose and is right to: a seat told to set a
variable it has already set goes looking in the wrong place.

**Why a false header is a security defect and not a typo.** The claim is
the reason nobody would look. A reader auditing whether this tool can
leak its environment reads that paragraph, believes it, and stops. The
charter names this class first among merged-diff defects, as comments
that lie about the code, and the specimen it names is a docstring about a
mail provider. This is the same shape on a disclosure surface.

**The conditional disclosure, stated honestly.** The schemeless branch is
reached only for a value this tool could not parse, which is exactly where
it has the least assurance about shape. A URL carrying userinfo,
`user:pass@host/path`, is schemeless under this test and would have been
printed verbatim to standard error, in a session whose output seats
routinely paste into run notes and pull requests. The redaction gate
would not catch it, because its three patterns are home paths, project
slugs and UUIDs.

**Nothing is disclosed today.** This sandbox's `BOARD_API_URL` carries a
scheme, no at sign and no query string, measured by predicate without
printing the value, so the branch cannot fire on it at all.

**What shipped.** The header now says what is true: the token is never
printed, the URL is printed in two places, both deliberate, and
therefore userinfo is masked before a value is named. `maskUserinfo` in
`tools/board/live-target.mjs` replaces a `user:pass@` prefix and is
anchored and slash-bounded, so a port and an at sign inside a path are
both left alone and the host, the port and the path all survive for the
seat reading the diagnostic.

**Guarded, and the guard is load-bearing.** Four tests. Against the
pre-fix function with the helper exported but not applied, nine pass and
the userinfo-echo test fails. After the fix, ten pass. The whole board
suite is sixty tests and all sixty pass.
