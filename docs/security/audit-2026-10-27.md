## 5. F37 — the file that promised it never prints the board URL prints it twice

**Severity: low, and latent rather than live.** Nothing was disclosed,
and that was measured rather than assumed.

`tools/board/post.mjs` says in its header that `BOARD_RUNTIME_TOKEN` and
`BOARD_API_URL` are read from the environment and that "this file never
prints either one". The token half is true, and it was checked on every
path: the dry run prints the Authorization header as a placeholder, the
environment faults name the variable rather than its value, and a non-2xx
response prints the board's own body.

The URL half is false in two places. The first has been there since the
file's first commit on 2026-10-26, which prints `POST <url>` under
`--dry-run`, where the URL is built from `BOARD_API_URL`. The second
arrived in #555 yesterday, in the new `BOARD_URL_SCHEMELESS` fault, which
names the unusable value on purpose and is right to: a seat told to set a
variable it has already set goes looking in the wrong place.

**Why a false header is a security defect and not a typo.** The claim is
the reason nobody would look. A reader auditing whether this tool can
leak its environment reads that paragraph, believes it, and stops. The
charter names this class first among merged-diff defects, as comments
that lie about the code, and the specimen it names is a docstring about a
mail provider. This is the same shape on a disclosure surface.

**The conditional disclosure, stated honestly.** The schemeless branch is
reached only for a value this tool could not parse, which is exactly where
it has the least assurance about shape. A URL carrying userinfo,
`user:pass@host/path`, is schemeless under this test and would have been
printed verbatim to standard error, in a session whose output seats
routinely paste into run notes and pull requests. The redaction gate
would not catch it, because its three patterns are home paths, project
slugs and UUIDs.

**Nothing is disclosed today.** This sandbox's `BOARD_API_URL` carries a
scheme, no at sign and no query string, measured by predicate without
printing the value, so the branch cannot fire on it at all.

**What shipped.** The header now says what is true: the token is never
printed, the URL is printed in two places, both deliberate, and
therefore userinfo is masked before a value is named. `maskUserinfo` in
`tools/board/live-target.mjs` replaces a `user:pass@` prefix and is
anchored and slash-bounded, so a port and an at sign inside a path are
both left alone and the host, the port and the path all survive for the
seat reading the diagnostic.

**Guarded, and the guard is load-bearing.** Four tests. Against the
pre-fix function with the helper exported but not applied, nine pass and
the userinfo-echo test fails. After the fix, ten pass. The whole board
suite is sixty tests and all sixty pass.

## 7a. F38 — incident 2's purged records are still fetchable, by ref name, from the public repository

**Severity: severe. This is the one finding in this report that needs the
owner rather than a seat, and the action is a GitHub Support request.**

**What was measured.** The ref sweep in §7 found fifteen pull request
head refs whose tips carry an unallowed match, and eleven of them are the
earliest eleven pull requests this repository ever had. Two of those,
`refs/pull/1/head` and `refs/pull/2/head`, carry the complete
`ursa-major/trial/` directory as it stood before the incident 2
remediation: seven files, 4,009,201 bytes, including
`task-001/outcome_record.json`, `task-001/outcome_record.html`,
`task-001/annotations.json`, `task-001/trajectory.md` and both files of
`task-001-all-sessions/`. Those are the artifacts incident 2 is about.
Counted on the two record files alone, 928 and 1,107 lines carry a
Class B home path or a Class C full UUID.

**Verified server-side rather than locally.** `git ls-remote origin
refs/pull/1/head refs/pull/2/head` returns the same two object names this
clone holds, so the refs are live on GitHub and not an artifact of a
local fetch. Anyone can fetch them from a public repository with one
command, by name, without knowing any object name in advance.

**The closure verification is where this got missed, and it is worth
stating exactly.** Incident 2's register entry records four checks on a
2026-09-20 fresh Actions checkout, one of which is that
`git cat-file -t 0794210` fails with "Not a valid object name", so the
bootstrap commit "is gone from the rewritten history rather than merely
unreferenced by a branch". In this clone, which fetched
`+refs/pull/*/head:refs/prs/*`, `git cat-file -t 0794210` returns
`commit`, and `git merge-base --is-ancestor 0794210 refs/prs/1` is true.
Another of the four checks used `git branch -r`, which lists
remote-tracking branches and therefore cannot see a pull request head ref
at all. So the verification was sound for the surface it looked at and
blind to this one, and the same is true of `git log --all` on a default
clone, because `--all` means the refs that were fetched.

**What this changes about the accepted residual.** The fix's clause (3)
records that the owner declined a GitHub Support cache-GC request,
"accepting that unreferenced commits remain SHA-addressable until
GitHub's own GC, with practical exposure low because no PR ever displayed
the paths". Two of those words are no longer accurate. The commits are
not unreferenced: they are the tips of two refs GitHub maintains and does
not garbage-collect, which is why they survived the force-push that
rewrote every branch. And the exposure is not SHA-addressability, which
requires knowing a 40-character object name. It is ref addressability,
which requires knowing the number 1.

**What the owner's options are, stated plainly and not chosen here.**
Ursa incident 2 was closed on the premise above, so this reopens a closed
incident rather than filing a new one, and that is the project manager's
call and not this seat's.

1. A GitHub Support request to remove the `refs/pull/*` refs and the
   associated object data for this repository, which is the request
   clause (3) declined on a premise this finding corrects. Support can do
   this; a repository owner cannot delete a pull request head ref.
2. Accept it again, now knowing the exposure is by ref name rather than
   by object name. That is a defensible decision and it is the owner's.
3. The nuclear option, which is to recreate the repository, and which
   costs every pull request number, every review and every Actions log
   this organization uses as its record. Named for completeness and not
   recommended.

**What this seat did not do, deliberately.** It did not fetch, open,
read, quote, or copy any record content, beyond counting pattern matches
per line and listing file names and byte counts. It did not delete or
rewrite anything. It did not contact GitHub. The charter's rule for a
found secret applies to found private data the same way: name where it
is, never reproduce it, and say whose action the remedy is.

**The generalisation, because the specific fix does not close the
class.** A pull request head ref outlives the branch, the pull request
and any history rewrite. So "we rewrote history" and "we deleted the
branch" are not remediations for anything that was ever pushed to a
branch with a pull request open on it. The redaction standard's §7 limits
section should say so, and the next audit of this seat should write it
there rather than leaving it in one finding. This run did not amend the
standard a second time because the wording of a remediation rule for a
closed incident is better written after the project manager and the owner
decide which of the three options above is taken.
