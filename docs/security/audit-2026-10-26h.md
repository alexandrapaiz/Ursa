## 4. F33 — the local checker hardcoded the one gate flag that decides whether an image is scanned

**Severity: medium.** Not a disclosure today. It is a gate mirror that
would have gone quietly wrong at the moment somebody fixed the gate.

`scripts/redaction-check.mjs` exists because the gate's three patterns
lived only inside the workflow, so the only way to ask the question was
to push and wait. Its header states the contract: the workflow is the
authority, the script reads the rules out of it, and there is nothing
here to drift. It read the patterns, the exclude directories, the
exclude files and the line-scoped allowance. It did not read the flags.
`const args = ['-rInE', pattern, '.']` was a second copy of a rule.

The flag that matters is `-I`, which tells grep to treat a binary file
as though it held no match. PWC-13, filed by run 12, asks HQ to remove
it, because this repository tracks 1,175 committed images that no gate
pattern has ever been applied to. So the two files were about to
disagree in the one direction that is silent: the gate would start
catching binary hits and the local checker, still passing its own `-I`,
would keep reporting clean on the same tree.

**Verified both ways.** A one pixel PNG carrying a fabricated home path
and a fabricated full UUID in an uncompressed `tEXt` chunk, beside a
text file carrying the same two strings, in a temporary git repository
outside this tree. Against the gate as it stands the checker reports the
text file and says nothing about the image, which is correct, because
the gate does the same. Against a copy of the gate with `-I` removed,
the pre-fix checker produced byte-identical output, which is the drift.
The probe was deleted after measuring.

**The second half, which the flags alone would not have fixed.** GNU
grep announces a binary hit on standard error, as
`grep: ./file.png: binary file matches`, and prints nothing on standard
output. The script captured standard output only, by way of
`execFileSync`, so even with the gate's flags read correctly it would
have seen nothing. This is the same trap PWC-13 names for the gate's own
`hits=$(...)` capture, arriving in a different file, and it is why that
entry says that applying the flag change without the redirect produces a
gate that looks changed and catches nothing.

**What shipped.** The flag cluster is read from the workflow. A gate
that stops declaring `r`, `n` or `E` exits 2 as a broken checker rather
than parsing output it no longer understands, which is the same contract
the patterns already had. Both grep streams are read, the binary notice
becomes a location-only finding printed as `path:-`, and anything else
on standard error exits 2 rather than being swallowed, because a partial
scan is not a clean one. Behaviour against today's gate is unchanged.

**Priced.** All three patterns across this whole tree with no `-I`:
zero binary matches, zero other lines on standard error, and the same
29 text hits the allowance already covers. Run 12 measured the first of
those numbers from the gate's side and this run measured all three from
the checker's side, which is a second instrument agreeing rather than
the same instrument twice.

**Guarded.** Three tests, and they fail against the pre-fix script,
which was checked rather than assumed: 13 passed and 2 failed on the old
file, 15 passed on the new one. One asserts the gate's flag cluster is
not duplicated into the script. Two pin both sides of the binary
surface, the skip while `-I` is there and the catch once it is gone,
using a PNG built at runtime and a gate derived from the real workflow
so that no pattern is copied into the suite.

**One method correction, for whoever re-runs any of this.** Run 12
recorded that `grep` on this sandbox's PATH is ugrep rather than GNU
grep. The sharper statement is that the harness installs a shell
**function** named `grep` which calls ugrep **and forces `-I`
unconditionally**. PATH `grep` is GNU grep 3.11, which is what
`ubuntu-latest` runs, and it is what Node reaches through
`execFileSync`. The consequence is specific and worth keeping: a seat
that verifies binary-file behaviour from bash cannot reproduce the gate
at all, before or after PWC-13, because its `grep` silently adds back
the flag under test. Use `/bin/grep`, or a script, and say which.

## 5. F34 — the gate republished an identifier a second time, one day after the fix was priced at three characters

**Severity: low, and the severity is not the point.** PWC-8 defect 3,
filed 2026-10-25 by this seat after the gate caught a vendor tracking id
and printed it into five public Actions logs. The entry says to apply
this one first if only one gets applied, because it is three characters
of pipeline and it closes a live publication path.

It was not applied, and on 2026-10-26 it fired again. Six
`redaction-gate` runs between 19:38 and 19:53 UTC, run ids 40388536800,
40389490399, 40389661182, 40389972396, 40390367634 and 40390743952, and
each one's log carries the matched value in full. Checked by counting
pattern matches in each log rather than by reading one and assuming the
rest.

What is different the second time is the class of thing published. The
first instance was a vendor's per-invocation tracking id. This one is a
board message identifier, belonging to a message Ursa's skill seat sent
to this seat. Neither needs rotation and neither is the owner's. The
mechanism cannot tell either of them from a session id, which is defect
3's own argument, and two instances in two days in two different seats'
lanes is the measurement the entry was missing.

Two things this run did about it, both inside its own write surface. The
redaction standard's Class C now names board and dispatch identifiers as
UUID-shaped and says to truncate them to eight characters, because every
seat handles them daily and nothing told anybody they trip the gate. And
PWC-8 carries the second instance, so whoever applies it can see that
the three-character change has now been owed twice.
