## 1. F60 — the pager decided its own completeness from a flag it never cross-checked

`tools/board/page.mjs` is, in its own header's words, "the only board read
in this repository that is allowed to be the denominator of a ratio." It
exists because two seats published wrong numbers on 2026-11-02 from a read
that silently truncated at 500 rows.

The walk stops on one line, `if (!page.saturated) break`, after which
`complete` is reported `true` and `ratioFault()` returns `null`, which is
the permission to publish a ratio. Until this commit that boolean came
only from the route, and `fetchMessagePage` turned an absent `saturated`
into `false` through `Boolean(body.saturated)`. That is the unsafe
direction: a route that stops sending the field, or renames it, makes the
pager stop after page one and call the result complete.

**The data to catch it was already in hand and read by nothing.** `limit`
was captured in the fetch result on line 144 and used nowhere in the file.

**Why no test caught it.** Every fake in `page.test.mjs` computes
`saturated: page.length >= ceiling` — honestly, from the row count. So the
case where the route is wrong about its own page was untestable by
construction, not merely untested.

**The fix.** A new exported `pageFilled()` derives saturation from the row
count against the page's own limit and takes either signal. A disagreement
between the two is recorded in `page_log` and counted in a new
`saturation_disagreements` field on the receipt, rather than smoothed over:
a route misreporting its own scope makes every other scope claim it makes
suspect too. Four tests, including the lying-flag case, the
missing-field case, an honest route producing byte-identical receipts, and
the four combinations of flag against count.

Behaviour against the live board is unchanged: 0 disagreements tonight.

## 3. F61 — the containment check every charter orders cannot run

This is the finding worth the owner's eye, and this run found it the way
findings should be found: a test refused to answer.

`tools/stack/repair-pending.test.mjs` skipped with "bootstrap refspec not
fetched; nothing to measure" on a clone this run had **already** repaired
with `tools/ensure-full-clone.sh`. The reason is that the repair tool
completes depth and widens the branch refspec, and says so, but does not
fetch `refs/pull/*` — deliberately, in a paragraph headed "WHAT IT DOES
NOT DO". That reasoning is sound and this finding does not argue with it.

The defect is the gap on the other side of it. Measured on this clone,
after repair:

```
$ git for-each-ref refs/prs | wc -l
0
$ git merge-base --is-ancestor refs/prs/664 refs/prs/672
fatal: Not a valid object name refs/prs/664
exit 128
```

The same question asked with refs that exist exits `0`: #664 **is**
contained in this branch. So the command the charters supply returns the
opposite of the truth.

**The direction is what makes it expensive.** `--is-ancestor` speaks
through its exit code and every non-zero value means NOT CONTAINED. A
missing ref is non-zero, so the error cannot be told apart from the answer
"no" in the idiom a seat actually writes, `... && echo contained`. Having
read "not contained", the seat follows the next sentence of the rule and
combines the branches by hand — rebuilding work that was already merged,
which is the exact waste the rule exists to prevent. It is also fault 1
from `ensure-full-clone.sh`'s own header, "non-zero means NOT CONTAINED —
the opposite of the truth", reached through a door that file does not
close.

**Scope: all eleven seat charters, seventeen occurrences**
(`grep -rc refs/prs prompts/*.md`). None says to fetch first.

Filed `urgent` in `docs/ideas.md` with two one-line remedies, because
`prompts/` is outside this seat's write surface and the text is identical
across eleven files, so it is one owner edit rather than eleven seat
edits. The preferred remedy names `origin/<branch>`, which exists in any
repaired clone: it removes a fetch rather than adding one and cannot
half-succeed. This run used that form for its own check, which is why it
noticed at all.

## 4. F59 — eleven workflows report another seat's pull request

The "Report this run to the board" step, identical in all eleven seat
workflows, identifies this run's pull request with:

```
gh pr list --state all --author "@me" --limit 1 --json url,body,headRefName
```

No `--head` filter. Every pull request in this repository is authored by a
single identity — measured across the last 30, all one login — so that
read returns the newest pull request in the repository regardless of which
seat is reporting. The step then posts its `url` and the first 2,000
characters of its `body` to the board as this seat's run report. The
owner's Runs window is, by `standards/operating-modes.md` §3, her only
window into a run, and it would attribute another seat's work to this one.
It misfires worst exactly when the portfolio is busy.

**Latent, and measured as such rather than assumed.** 561 run rows across
eleven seats on the live board, and **zero** whose `run_url` is a GitHub
Actions run; every one comes from the resident host, which uses a
different poster. These workflows last fired 2026-10-17, the day HQ
decision 056 retired the schedule. So the defect has never produced a
wrong row. It fires on the first `repository_dispatch` or
`workflow_dispatch`, both of which these files still declare.

The fix is one line per file and is already the shape of the fallback on
the very next line of the same step. It is in `.github/workflows/`, so the
owner is the only applier; it sits as row 10 of the ranked table in
`docs/agents/pending-workflow-changes.md`, with a finding number rather
than a queue number, per the rule the previous run wrote there.
