First run of the Ursa security seat (ADR-20), so this is the baseline:
a full-history secret scan, a dependency audit of all three packages,
the public and private boundary, the network-facing surface of the
overlay, the Actions posture, and the prompt injection surface. Charter
is prompts/security-agent.md. The debug sweep ran first and is recorded
at the end.

Nothing in this report contains a secret value or an exploit payload.
Where a weakness was verified, it was verified against our own code
running locally, which is what the charter allows.

No secret has ever been committed to this repository. That is the

## 1. Bridge run channel executed on cross-site POST — High, fixed

`ursa-major/src/bridge/index.ts` runs a local HTTP listener on
127.0.0.1:7817 whose `POST /run` spawns `ursa run <project>`. It
computed an allowed origin and used it to decide which CORS headers to
echo back, then fell into the execute branch regardless of the answer.

The gap matters because a POST carrying no content-type is a CORS
simple request. The browser sends it with no preflight and then hides
only the response. So any page open in the owner's browser while the
bridge was running could spawn a run on her machine, against her
Claude subscription, writing to her `.ursa/` directory, and never need
to read the reply it was denied. DNS rebinding was not needed and would
not have helped, since a rebound name still sends its own origin.

Verified before the fix against a bridge running locally: a POST
carrying `Origin: https://attacker.example` reached the execute branch
and spawned the child process. After the fix the same request returns
403 and nothing spawns.

The fix refuses before `execFile` rather than after, and refuses a
request with no `Origin` header too, since every browser sends one on a
cross-origin POST and its absence never describes the caller this
channel exists to serve. The hosted overlay is already in
`allowOrigins`, so legitimate use is unchanged. Four tests in
`ursa-major/src/bridge/run-channel.test.ts` hold the gate shut.

## 2. Sync route accepts unauthenticated writes — High, queued

`ursa-major/overlay/app/api/sync/[key]/route.ts` accepts `PUT` at any
key matching 64 hex characters, with no authentication, no rate limit,
and `allowOverwrite: true`. Two consequences.

Anyone can write up to 2 MB at any key they invent, without limit. The
blob store is the owner's and it is billed to her, so this is a cost
and capacity exposure with no ceiling on it.

Anyone who learns a real blob id can overwrite that user's payload.
Confidentiality holds regardless, because AES-GCM means the server
never had the plaintext and an attacker cannot produce valid
ciphertext. What they can do is destroy: replace the blob with bytes
that fail authentication, and the overlay shows "cannot decrypt — wrong
passphrase?" forever. The blob id travels in the request URL, so it
reaches Vercel's access logs, the browser's history, and any proxy in
between. It was designed as a name, and names leak.

This needs a write credential or a proof of possession of the AES key,
which is a design decision rather than a fix, so it is in the ledger.

## 3. Pasted `[step N]` could forge a stated verdict — Medium, fixed

`ursa-major/src/verdict.ts` flattens the user's messages into a
transcript whose only structure is a `[step N]` prefix. A message that
quotes a web page, a file, or an issue containing its own marker
therefore arrived at the model as two turns.

The designed defense does not catch this. Quote verification exists to
discard a hallucinated quote, and it works by checking that the words
appear verbatim in the trace. When the words were pasted in by the
user, they do appear, so a forged "perfect, thank you" verified and
came back as `accepted: true`. Confirmed against the real function with
a stub runner.

This is worth more than its blast radius suggests. Acceptance is the
label the outcome record carries, the thing Ursa declines to infer from
retention, and the thing a lab is buying. A forged declaration is worse
than a missing one.

Fixed two ways. The marker is neutralized inside the body, where it
still reads the same and bounds nothing, so only real turns reach the
model. The transcript is wrapped in explicit markers and named as
untrusted content in the instruction. A model that quotes the
neutralized form now fails verification against the original text and
the session stays undeclared, which is the safe direction.

The distiller, `ursa-major/src/tuning/distill.ts`, embeds the same
untrusted content through `JSON.stringify`, which escapes it into a
single string literal and cannot be broken out of the same way. That is
the better pattern and the verdict reader was the one place not using
it.

## 4. Actions and secrets — Medium, queued as PWC-5 and PWC-6

The runner's token cannot write `.github/workflows/`, verified by
attempting it this run as `docs/agents/pending-workflow-changes.md`
asks. The two entries are queued there for the owner.

**Actions are pinned to mutable tags.** `anthropics/claude-code-action@v1`
appears 15 times, `actions/checkout@v4` 12 times, `actions/setup-node@v4`
once. A tag can be moved. Whoever moves one gets a step running with
`contents: write`, `pull-requests: write`, `id-token: write`, and the
job's secrets in its environment. Pinning to a commit SHA with the tag
in a trailing comment is the standard answer and preserves behavior
exactly.

**`PROJECTS_TOKEN` is distributed to all eleven seats and read by
none.** It appears exactly once per workflow, in the job-level `env:`
block, and nowhere else in any file. Only the exo and pm charters
mention it, and `docs/sprints/pending.md` records it as still unset. A
job-level secret is readable by the agent step, which is the precise
concern the security workflow already documents for
`SLACK_WEBHOOK_URL`, where the value is deliberately scoped to the one
step that needs it. The same reasoning should apply here.

What is already right: no `pull_request_target` anywhere, no
`issue_comment` trigger, and no `github.event.*` value from an
untrusted actor reaching a `run:` block or a prompt. The only template
expansion into a prompt is `inputs.owner_instructions`, and
`workflow_dispatch` requires write access, so that input is an owner or
HQ instruction by construction, which is what the charter intends. The
redaction gate runs `contents: read` and is correctly minimal.

One consequence worth stating plainly, since it is structural rather
than a defect. `agent-pm.yml` holds `actions: write` so the standup can
dispatch other seats, and a dispatch carries `owner_instructions`
straight into another agent's prompt. A PM run that was successfully
steered by something it read could therefore steer a second seat. The
mitigation today is that agents read a repository only the owner merges
into. It is worth not widening that.

## 5. One shared salt for every user — Medium, queued

`SALT = 'ursa-overlay-v1'` is a single application-wide constant in
both `ursa-major/src/bridge/crypto.ts` and
`ursa-major/overlay/lib/crypto.ts`. The code documents this as a
deliberate tradeoff, and the reasoning given is sound: the server must
not learn whose blob it holds, so there is no per-user salt to fetch.
Two consequences follow anyway and should be recorded rather than
rediscovered.

The work of attacking one passphrase is the work of attacking all of
them. 600,000 PBKDF2-SHA256 iterations is a real cost per guess, but it
is paid once per candidate across the entire user base rather than once
per user. The comment's conclusion, that the passphrase must therefore
be strong, is correct, and nothing in the product currently enforces or
even measures that.

Two users who choose the same passphrase derive the same blob id. With
`allowOverwrite: true` they silently overwrite each other. That is a
data-loss bug as much as a security one, and it arrives exactly when
the product succeeds.

The rest of the construction is sound. 512 bits are derived and split,
the AES key never leaves the client, the blob id is the other half, and
the IV is random per encryption and prepended. Knowing a blob id
reveals ciphertext only, as the comment claims.

## 6. Sync blobs are world-readable at a guessable URL — Low

The route writes with `access: 'public'` and `addRandomSuffix: false`,
so each blob also sits at a predictable public URL that bypasses the
route entirely. Confidentiality still rests on the encryption rather
than on the URL, which is the right place for it. What is lost is the
ability to rate limit reads, audit them, or revoke one. Related to
finding 2 and best decided with it.

## 7. Dependencies

`ursa-major/overlay`: clean, zero advisories.

`ursa-minor`: 8 advisories, 1 critical and 5 high. The critical is
`next` at a version below 16.3.6, carrying unauthenticated remote code
execution in the image optimization API when AVIF files are used, plus
a Windows-hosted variant. `npm audit` reports the fix as 16.3.6, which
is not a semver-major move from the declared range. The high entries in
`postcss` and `sharp` clear with the same upgrade. `fast-uri`,
`js-yaml`, and `nanoid` clear with a plain `npm audit fix`. This is the
public marketing site, so the exposure is real but the site has no user
data behind it. Not applied here, because a Next major-minor bump
touches the frontend seat's build and belongs in a PR that can be
checked visually.

`ursa-major`: 6 advisories, all in the `vitest` and `vite` dev chain
and none in anything shipped. The highest-rated one requires the Vitest
UI server to be listening, which this project never starts. `nanoid`
clears with a plain `npm audit fix`. The rest need vitest 5, a breaking
change for a test runner, which is engineer work rather than a security
fix.

No Python in this repository, so the charter's pipeline-image check
does not apply. There is no `mcp/server.py` here either; that section
of the charter is inherited from alexandria and has no Ursa surface
yet.

## Public and private boundary

Clean. `digests/` and `site/content/digests/` have never existed in
this repository, in the tree or anywhere in history. `.ursa/`, which
holds the raw outcome records, is gitignored at the root and has never
been committed. `.env` and `.env.*` are ignored at the root, which
covers the subprojects whose own ignore files list only `.env*.local`.

The redaction gate in CI covers the three classes from Ursa incidents 2
and 4: home paths with a real username, Claude Code project slugs
carrying a machine path, and full session UUIDs. It runs on every push
and pull request. It passed against the current tree.
