## 2. F63 — the prober's saturation abstention was dead code on one of its three routes

**Severity: medium.** An instrument reporting a measurement it did not
make. Fixed in this run.

`tools/board/read-filters.mjs` decides whether a board read's filter
actually filters, by comparing an unfiltered count against the count
under a value that cannot match. The whole method rests on the
unfiltered read not having filled its page, because once rows are being
dropped a filter that matched everything and a filter that did nothing
return the same number. The file's own header says so in capitals, and
`verdict()` implements it:

```js
if (base.saturated) {
  return { verdict: 'UNMEASURABLE', why: `the baseline page filled at ${base.count}, so an equal count proves nothing` };
}
```

**That branch could never be taken on the events route.** `read()` sets
`saturated: Boolean(body.saturated)`, and the events route sends no such
field. Read from the board's own source rather than inferred from
responses:

| Route | Reply includes | api.py |
|---|---|---|
| `/api/messages` | `limit`, `saturated` | line 1327 |
| `/api/runs` | `saturated` | line 1410 |
| `/api/events` | `events` and nothing else | line 709 |

So for events, `body.saturated` is `undefined`, `Boolean(undefined)` is
`false`, the guard is skipped, and the tool prints a count from a page
that filled as though it were an answer.

**It was doing exactly that when this run arrived.** The declared
2-hour events window returned 489 of the 500 asked for, 97.8% of a
page, and the tool printed `489 rows unfiltered` under a summary line
reading `0 unmeasurable`. The same read had been over 500 minutes
earlier, which is how this was found at all: the live assertion in
`read-filters.test.mjs` went red.

**The bias runs one way, which is why this is medium and not low.** A
row the page never reached looks like a row that does not exist, so the
instrument is least trustworthy exactly when the board is busiest. The
board's own source states the principle this seat was failing to
apply, at api.py line 2107: "an instrument must treat a saturated page
as a failed read, not as [an answer]".

**The repair.** The board is HQ's and not a seat's to change, so the fix
is on the reading side. `saturationOf(body, rowsKey, limit)` is now
exported and believes the field where a route sends it, and otherwise
infers it the way the board does, `len(rows) >= applied`, from the limit
the caller asked for. The board clamps `limit` to `[1, 2000]` (api.py
line 705) and this tool asks for 500, so the asked-for bound is the
applied bound and the comparison is exact rather than a guess. Four
tests pin it, including the case where the limit is unknowable, where
the honest answer is "not measured as saturated" rather than an
invention.

## 3. F64 — two declared windows the board had outgrown, and four claims that had silently stopped being made

**Severity: medium.** Fixed in this run. Same root cause as F63 and
found with it, filed separately because the repair is different: F63 is
a guard that could not fire, F64 is the condition that was firing it.

The probe windows are declared per route and were chosen against
2026-10-18 traffic. Nothing recorded what traffic, so there was no way
for a later seat to tell a measurement from a habit, and neither was
revisited as the board got busier.

**The events window.** `since_hours=2`, re-measured at 05:0xZ over a few
minutes: 493, then 488, then 489, against a 500-row page. A window that
fills on any busy minute.

**The messages window, which is the worse half.** `since_hours=6`
unscoped returned 500 and `saturated: true`. That route *does* report
saturation, so the guard worked, and four of the six message probes —
`to_company`, `from_company`, `to_seat`, `from_seat` — had been
reporting UNMEASURABLE on **every** run. The tool prints "an
unmeasurable filter is not a passing one" beneath them, and its summary
line still read `14 probed, 10 measured`. So the instrument was honest
about each individual claim and the headline number counted claims it
had abandoned.

**Re-measured, so the new windows are a reading and not a preference:**

| Route | Window | Rows of a 500-row page |
|---|---|---|
| events | 2h (old) | 493 / 488 / 489 |
| events | 1h | 268 |
| events | **0.5h (new)** | **127** |
| events | 0.25h | 60 |
| messages, unscoped | 6h (old) | 500, saturated |
| messages, unscoped | **2h (new)** | **239** |

Widening is the wrong direction and the test that caught this says so in
those words. A wider window here does not collect more evidence, it
collects the same newest 500 rows and loses the rest, so it buys a
number that looks bigger and means less. The messages casing probe needs
a genuinely wide window for a real reason and pages it through
`pageAll`, which is why shortening `window` does not touch that claim.

**Before and after, same command:**

```
$ node tools/board/read-filters.mjs      # on arrival
14 probed, 10 measured, 0 inert, 4 unmeasurable.

$ node tools/board/read-filters.mjs      # after
14 probed, 14 measured, 0 inert, 0 unmeasurable.
```

Each window now carries the count it was chosen against and the date of
that reading, next to the declaration, so the next seat can tell which
it is. An adaptive window that searches for a measurable one is the
better long-term answer and is filed as a ledger entry for the engineer
rather than written in a security run.

### The test that caught it was also the test that cried wolf

`read-filters.test.mjs` asserted `plain.body.events.length < 500` with
the message "the 2h events window now saturates; widen nothing, shorten
it". The instruction was right and the mechanism around it was wrong,
for two reasons.

It fails on a property of the board's traffic rather than of the code
under test, so every seat's suite goes red together on a busy night for
a defect none of them introduced, and the repair is to edit a number by
hand. And a filled page is the one condition this entire file exists to
call UNMEASURABLE, so the test was stricter than the tool's own reading
of the same state.

It now abstains and names the number, which is what the tool does. It
also reads the window from `ROUTES` instead of carrying a second copy:
the two had both said `since_hours=2` and would have drifted the moment
either was re-measured, which is precisely what happened an hour later.

Both new behaviours were verified by forcing them rather than reasoned
about. With the window temporarily set to 72 hours, the live test
abstains with `SKIP the events window saturates, so filtering it cannot
be distinguished from not filtering it; shorten ROUTES.events.window`,
and the window-sanity test fails with the stale window named. The window
was restored and the suite re-run.

## 4. F65 — a history claim scoped to every ref, so another seat's branch turns it red

**Severity: low** as exposure, and worth the entry for its failure mode.
Fixed in this run.

`tools/root-entries.test.mjs` asserts that no root-level dot-entry has
ever existed in this repository's history outside a three-name
allowlist, which is what makes `.gitignore`'s blanket `/.* ` rule safe.
It measured that with `git rev-list --all --objects`, which walks every
ref the local clone holds, and a seat run's clone holds every other
seat's unmerged branch. So the verdict depended on which branches
existed on the remote at clone time.

**What that cost, measured.** Ursa's PM seat committed
`.claude/settings.json` at 04:35:26Z on branch
`ursa-pm/2026-11-02-message-12` (PR #683), to install HQ's secret-print
hook, and correctly extended the allowlist to four names on that same
branch. Twenty-three minutes later this seat's clone — which holds those
commits, because it fetched the remote's branches, and not that
allowlist change, because it is not on that branch — went red with "a
root dot-entry in this history is neither on the allowlist nor in the
pinned scratch list, so the inversion may have a false positive after
all".

Nothing was wrong. Both seats were correct. The test was asking a
question neither of them could answer from their own branch, because the
new entry and the allowlist line that explains it arrive together and
only on the branch that holds both.

**The repair.** The assertion is scoped to `HEAD`, which is the history
this branch is a claim about and the history that will be on `main` if it
merges. Entries reachable only from other refs are still reported,
because the information is worth having, as a diagnostic naming them and
the branch that owns the explanation:

```
# root dot-entries on other refs but not in this branch's history: .claude
  -- if one of those branches merges, the allowlist here has to name it,
  and that branch is where it belongs
```

This seat did **not** add `.claude` to the allowlist on this branch. PR
#683 already does it, and writing a second version of another seat's
change is what the open-PR rule exists to prevent. The gate on `main`
will be correct when #683 merges, and correct before then, which it was
not.

## 5. F66 — the hook that should be installed arrives outside the sentence that protects workflows

**Severity: medium, and latent until PR #683 merges. Status: proposed,
for the owner and HQ.** Not fixed here, because the repair is a line in
charters and this seat may not edit charters.

**This is not an objection to #683.** The guard should be installed, the
standard requires it, and §7 below is this run's own evidence for why.
The finding is that the set of paths this organization protects did not
grow when a new path with the same reach did.

**What #683 adds.** `tools/check-secret-print.py`, and
`.claude/settings.json` registering it as a `PreToolUse` hook matching
`Bash|Write|Edit|MultiEdit|NotebookEdit`:

```json
"command": "python3 \"${CLAUDE_PROJECT_DIR:-.}/tools/check-secret-print.py\" --hook"
```

**What that means.** After #683 merges, those two committed files run a
command before every Bash, Write and Edit in every later seat run, in
runs that carry `--permission-mode bypassPermissions`, `contents: write`,
`pull-requests: write` and live credentials. Whoever controls the
content of either file controls what executes there. That is the same
reach `.github/workflows/` has.

**And the protection is not the same.** Measured, not assumed:

- Every seat dispatch, including the one that opened this run, says
  "never touch secrets or workflows" in those words. Neither path is a
  workflow and neither is a secret.
- No committed rule names `.claude/` as protected. `grep` over
  `prompts/` and `docs/standards/` returns three mentions and all three
  are descriptive: two in `prompts/exo-agent.md` explaining that Ursa
  has no `.claude/` directory, one in `lessons.md` stating where HQ
  registers the hook.
- There is no `CODEOWNERS` file in this repository, at either location
  GitHub reads.
- `redaction-gate` is the only workflow that fires on pull requests. It
  scans for three private-data patterns and has `contents: read`. It
  would not notice a change to either file, and it is not its job to.

**Why it is medium and not high.** The owner merges every pull request
here, so landing a change to either file requires getting it past her
review, and that is a real control. The exposure is that the review has
no marker telling her which diffs carry this reach, where
`.github/workflows/` has eleven charters, every dispatch and this seat's
own audits all pointing at it. A hook edit buried in a thirty-file
housekeeping pull request reads like housekeeping.

**The repair, which is three lines and none of them this seat's.**

1. Add `.claude/` and `tools/check-secret-print.py` to the "never touch"
   clause in the seat charters and in the dispatch text, alongside
   workflows and secrets. This is the one to do if only one is done.
2. A `CODEOWNERS` entry for both paths, so GitHub itself marks the diff.
3. HQ's own copy of this: the same two files are in five repositories by
   `lessons.md`'s count, so if the clause is missing here it is likely
   missing in the standard that vendored them.

## 7. This run's own L-X5 violation

Recorded as `INC-2026-11-02-the-security-run-printed-twelve-bytes-of-three-live-credentials-while-reading-the-note-about-the-unrun-checker`
in `docs/agents/incidents.md`. Summarised here because a security report
that audits everyone else's conduct and not its own is not an audit.

In its first minutes this run needed the board's base URL and ran a
pipeline over `env`, truncating each value to its first twelve bytes
with `sed`. Three of the matched variables were live credentials. L-X5
is "secrets: presence and length, never the value", and twelve bytes is
a value.

The prefix was not printed anywhere durable. It is in this run's
transcript and not in any commit, pull request or report, and this entry
does not reproduce it. No rotation is required, and that is a statement
about where the bytes went rather than a judgement that a partial
credential is acceptable.

**Measured against the checker rather than asserted.** The command was
passed to `tools/check-secret-print.py` from PR #683's branch:

```
$ python3 /tmp/csp.py --command 'env | grep -iE "board|epito|..." | sed -E "s/(=.{0,12}).*/\1…/"'
<command>:1: X5-ENVDUMP  a bare `env` sent somewhere dumps every variable
in the environment, secrets included
```

So the guard that is not yet on `main` catches this exact command, by
name, and would have refused it before it ran. This run had no `.claude/`
directory, because `.gitignore` line 76 blanket-ignores root dot-entries
and the carve-out is still unmerged, so no hook was registered and
nothing checked the command.

**Why this belongs in the report and not only in the register.** The
note that triggered this run is about one sentence: being referenced is
not being run. The seat that received that note then violated, inside
twenty minutes, the exact rule whose checker was referenced in this
repository and run nowhere in it. That is not an illustration anybody
arranged. It is the measurement, and it is the strongest argument this
report can make for merging #683 and for F66.
