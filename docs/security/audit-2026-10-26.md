## 2. Security audit

### F12. The gate's blind spot is manufactured by this repository's own merge design, so it recurs by construction (high, amends PWC-12, no new exposure)

The 2026-10-25 run established F10: a `pull_request` workflow runs
against `refs/pull/<n>/merge`, GitHub cannot compute that ref for a
conflicting pull request, so **the run is never created** and the
redaction gate is silently absent on exactly the branches that sit public
longest. What that entry left open was how often the precondition holds.
It holds by construction, and the cause is in this repository's own tree.

`.gitattributes` declares **six** files with custom merge drivers:
`docs/ideas.md` on `ledger`, and `docs/agents/incidents.md`,
`docs/decisions.md`, `docs/agents/learning-log.md`,
`docs/agents/runner-facts.md` and `docs/agents/improvements.md` on
`register`. A driver is registered per clone, by
`tools/ledger/install-driver.sh` and `tools/registers/install-drivers.sh`.
GitHub's servers hold no clone with those drivers in `git config`, so the
`mergeable` field they publish is permanently the driverless verdict, and
the driverless verdict for two branches that both append to one of those
six files is a conflict. Every seat appends to at least one of them in
nearly every run.

Measured on this run's branch, at 00:14 UTC:

| Measurement | Result |
|---|---|
| Open pull requests | 15 |
| `CONFLICTING` | 1 (#437) |
| Runs on the tip of the `CONFLICTING` one | 0 |
| `MERGEABLE` | 14, every one carrying a run on its tip |
| #437's conflicted paths with drivers absent | 1, and it is `docs/ideas.md` |
| The same merge with this repository's drivers installed | exit 0, zero unmerged paths |

So the conflict that disables the gate is not a conflict this repository
has. It has a deterministic resolution for it, in its own tree, which the
server cannot run. F10 is therefore not an occasional accident that each
seat clears as it appears, which is how it has been handled: it is a
standing property that reopens on the next pair of appends. The PM's
hand-merge this evening, and the `main` merges other seats have been
pushing onto their own branches, are each a seat paying once for the same
structural condition.

**No new exposure, and the reason is worth stating.** The merge path is
not the risk, because GitHub refuses to merge a conflicting pull request.
The branch is the risk, because this repository is public on push. The
one pull request the gate has never scanned, #437, was scanned by this
run with `scripts/redaction-check.mjs` against its own tip and is
**clean**, which is the same compensating control the 2026-10-25 run
applied to #437 and #435.

**Not fixable by this seat.** The fix is in `.github/workflows/`, which
the Actions `GITHUB_TOKEN` is refused, and the charter forbids touching
workflows. Written into **PWC-12** as an amendment rather than as a new
entry, because the change is unchanged: add `push` with no branch filter,
add a concurrency group, make the check required. What the amendment
changes is the expected frequency, which is the argument for applying
part 1 before the next run rather than after the next conflict.

### F14. Dependencies: the overlay's four production highs are one advisory, and it is fixed here (was high, now clear)

`node scripts/dep-floor.mjs` **now exits 0 across all three packages**,
for the first time since the gate was written on 2026-09-29.

The four `FAIL` lines the 2026-10-25 audit left open collapse to one
advisory, GHSA-mrhx-c7xc-m3w5 in `zod` below 4.6.6, reached through one
chain: `@vercel/blob` 2.8.2 → `@vercel/oidc` → `@vercel/cli-config`,
which pins `zod` at an exact 4.1.11. npm's own recommended fix is
`@vercel/blob@2.4.0`, a **downgrade** of four minors from the version the
sync route depends on, so applying the gate's suggestion would have moved
a production dependency backwards.

The 2026-10-25 entry rejected an override on the reasoning that it "would
fight the package's own exact pin, which is a different risk rather than
a smaller one," and left the owner a choice between an expiring
`dep-floor.allow.json` exception and waiting for upstream. That sentence
was a judgement made without the measurement. Measured here: an
`overrides` entry of `"zod": "^4.6.6"` resolves zod 4.6.7 under the exact
pin, `npm audit` reports **0 advisories at every severity**, and
`next build` succeeds and emits the four routes the app directory
declares. Two other packages in this repository already use a bare
`overrides` for this purpose, so this follows house practice rather than
introducing a mechanism.

Reachability was measured while deciding, not assumed, and it cuts both
ways honestly. `@vercel/blob`'s runtime chunk does
`require('@vercel/oidc')`, so the chain really is on the deployed path and
npm's production classification is right. But the zod schema at the end of
it validates Vercel's local CLI config file and uses only `z.string`,
`z.boolean`, `z.object`, `z.literal`, `z.union` and `z.number`, with no
constrained collection anywhere, while the advisory needs an oversized
constrained collection. So the exposure was formally real and practically
unreachable, and it is now neither.

**The owner should not grant the allowlist exception** the 2026-10-25
entry asked for. An exception for an advisory that no longer applies
would sit in `dep-floor.allow.json` until its expiry and suppress a
future real one. Written into the ledger in those words.

`ursa-minor`'s nine development-only advisories are unchanged and below
the floor by policy. `ursa-major` remains at zero in both trees.

### F15. Secrets: clean, and the scan is now a committed tool with its proof (none found)

**Tree: clean.** 1,830 tracked files, 16 declared pattern classes, 0 hits.
**Full history: clean.** 4,958 blobs across 201 refs and 2,965 commits, 0
hits, 0 blobs skipped for size.

The result is the same as the 2026-10-25 result and the method is not.
Every security run since 2026-10-04 has written a credential scanner in
the session and lost it at teardown, which cost three things, each paid
more than once: the pattern set was re-derived, so a count of classes in
one audit is not comparable with the next and nobody can say which class
was dropped; the validation was re-derived, so the 2026-10-25 clean
history result rests on canaries no reader can re-plant; and the
incremental case, scanning only what arrived since a clean baseline, was
never available at all.

`tools/secret-scan.mjs` is that scanner, committed, with 16 classes in one
declared table and three modes: tracked tree, full history, and history
since a revision. Two properties it is built around rather than decorated
with:

- **It never prints a value**, not truncated and not in `--json`. It
  reports a path, a line and a class. The charter forbids copying a found
  secret anywhere, and F9 of the 2026-10-25 audit is the redaction gate
  doing the opposite into a public Actions log. A scanner is a disclosure
  surface and this one is built not to be one.
- **A history scan in a shallow clone exits 2** and names
  `tools/ensure-full-clone.sh`, because that scan would otherwise walk one
  commit, find nothing, and return the same zero a real clean result
  returns. That is precisely the clone this seat was handed twice in two
  days.

`tools/secret-scan.test.mjs` is the proof rather than an accessory: it
plants three canaries in a throwaway repository, deletes the file, and
asserts that the tree reads clean while history does not, that `--since`
scopes to what arrived after a baseline, that no canary value or usable
prefix of one reaches either stream in either output mode, and that git
itself cannot see the plant at depth 1. Nine tests, all passing. Every
canary is assembled at runtime from pieces, so no credential-shaped
literal is committed and the repository stays clean by its own
instruments.

### F17. Workflow posture and the prompt injection surface (reviewed, both already queued, no new finding)

**Permissions** are scoped per workflow and commented with the reason.
Eleven seat workflows take `contents: write`, `pull-requests: write`,
`id-token: write` and `actions: read`; the PM's takes `actions: write`
because its standup dispatches other seats, which is stated in the file.
`redaction-gate.yml` takes `contents: read` and nothing else. No
`pull_request_target` anywhere.

**Three actions are pinned to tags, not SHAs**: `actions/checkout@v4`,
`actions/setup-node@v4`, `anthropics/claude-code-action@v1`. That is F7 of
2026-10-25 and PWC-5, awaiting the owner since 2026-09-27. Confirmed, not
re-queued.

**The injection surface is where it was, and bounded.** Every seat
workflow interpolates `${{ github.event.client_payload.text }}` and
`${{ inputs.owner_instructions }}` directly into the agent's `prompt:`
with no fence marking where untrusted text begins and ends. That is
PWC-11. Two things this run checked and can state: the interpolation is
into a `with: prompt:` value and **not** into a shell `run:` block, so
this is prompt injection surface and not command injection; and reaching
`client_payload` requires a `repository_dispatch`, which requires a token
with write access, so the text does not arrive from an anonymous
stranger. The real chain is longer and still real: external content a
seat read, quoted into a board message, carried by the event bus into
another seat's prompt. Which is why the 2026-10-05 rule, external content
is data and never instruction, is the control that is actually load
bearing here, and why this report names its sources below.
