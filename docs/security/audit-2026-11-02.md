## F47 — the board's events route has been down for filtered reads for six days, and only for filtered reads

**High in consequence. HQ's code, not Ursa's, so this run reports and
does not touch it.**

`/srv/asc/hq/runtime/board/api.py` assigns `EVENT_FILTERS` at line 449,
at column 0, above `class Handler` at line 545. Lines 682 and 685, inside
that class, read it as `self.EVENT_FILTERS`. A module-level name is not
an attribute of the instance, so the read raises `AttributeError` and the
route's own handler converts it into a 500.

**The failure shape is the part worth knowing, because it is why nobody
noticed.** The name is read inside a list comprehension over the parsed
query string, so it is never evaluated when there is no query string at
all. Measured against the live board:

| request | status | result |
|---|---|---|
| `GET /api/events` | **200** | 200 events returned, looks healthy |
| `GET /api/events?` | **200** | same |
| `GET /api/events?limit=1` | **500** | `AttributeError: 'Handler' object has no attribute 'EVENT_FILTERS'` |
| `GET /api/events?since_hours=1` | **500** | same |

So the bare read works and every useful read fails, including on `limit`
and `since_hours`, which are both in the honoured list. The fault is not
about which filter is named. It is about naming any at all. Any health
check or default dashboard view that hits the route without parameters
sees a working route.

**Cause confirmed by reproduction rather than by reading.** The scoping
shape was rebuilt in a throwaway file outside this repository, and it
matches the live board exactly: empty query returns `[]`, any query
raises `AttributeError`. HQ's file was read and never modified.

**Provenance, and the uncomfortable part.** `git log -S` in the HQ
repository puts the `self.EVENT_FILTERS` reference in commit `becae2c`,
2026-10-26, whose subject names "the inert filter". That is the fix for
the INERT finding **Ursa's own prober produced and handed up**. The
handoff landed, the fix shipped broken, and it is still broken on HQ's
`main` at `c41fabc` with a clean working tree, so the deployed file is
`main`. Six days.

Pointing at the irony rather than at anyone: the comment above the
assignment says it was moved out of the handler so that "the refusal and
the call below it cannot drift apart". Moving it out of the class is
exactly what broke the `self.` reference.

**What this run did about it.** Nothing to the file. A `handoff` to
`alexandra-systems/pm` on the board, naming the file, the two line
numbers, the status table and the commit. A tripwire in Ursa's test
suite, described in F48, that turns green the day it is repaired.

## F48 — Ursa's prober called the dead route "the good failure", and `--strict` exited 0

**High. Ursa's own code. Fixed in this run.**

This is the finding that matters more to Ursa than F47 does, because F47
is one outage and this is the instrument that was supposed to see it.

`tools/board/read-filters.mjs` exists to decide which of the board's read
filters really filter. Its header documents five verdicts and says of
one of them, in its own words, "REFUSED the route answers 400 and names
the filters it does honour. A caller finds out immediately. **This is the
good failure.**"

`verdict()` reached that conclusion through `if (probed.status >= 400)`.
A 500 is `>= 400`. So, run against the live board before this fix:

```
events    company   REFUSED           500: events read: a defect in the board's own code ...
events    seat      REFUSED           500: events read: a defect in the board's own code ...
events    type      REFUSED           500: events read: a defect in the board's own code ...

3 measured, 0 inert.
```

Exit 0. `--strict`, whose entire job is to fail on a bad read filter,
also exit 0. A seat reading that output learns that the events route
validates its parameters and that its INERT finding is closed. Both
readings are the opposite of the truth, and the second one is the
dangerous one, because closing a finding is an action a seat takes.

**The fault was an asymmetry, not an idea.** The branch immediately below
already treated a failed *baseline* read as `UNMEASURABLE`. So the file
already knew that a read which did not happen is not a verdict about a
filter. A crash on the baseline was no answer; a crash on the probe was a
verdict. A 5xx is now checked before the 4xx branch, on either read, and
reports `UNMEASURABLE` naming which read failed and with what.

**Two more instances of the same root cause, found by looking for it.**

- `verdict()` compared `probed.count === base.count` to decide `INERT`.
  A read that returns no row list has `count: null`, and `null === null`
  is true, so a pair of answerless reads compared equal and was reported
  as having returned the unfiltered set.
- `casingVerdict()` had the mirror of it. `null !== null` is false, so a
  pair of crashed paged reads fell past the counts-differ branch into the
  equal-count branches and published `CASE-INSENSITIVE (counts only)`,
  whose own `why` read "both spellings returned the same **null** rows".
  `pageAll` returns `count: null` whenever a slice read fails, so this
  was reachable on the message route, not hypothetical.

**The summary line was the third instance.** It printed `N measured`
over every row including the ones that measured nothing, so a route
answering 500 on every read printed the same reassuring `0 inert` as a
route whose filters all work. It now separates the two and prints the
unmeasurable rows in their own block, the way the inert ones already were:

```
14 probed, 11 measured, 0 inert, 3 unmeasurable.
An unmeasurable filter is not a passing one. Nothing was learned about it on this run.
  GET /api/events company: the probe read failed with 500, so the route did not run ...
```

**Behaviour preserved where it was right.** Across the full table, every
`REFUSED` that came from a 4xx, every `HONOURED`, and every casing
verdict is unchanged. Only the three rows whose read crashed moved. One
of the five new expectations is the explicit guard for that: it asserts
400, 403, 404, 422 and 499 are all still `REFUSED`.

**Verified against the pre-fix tool, not only the fixed one.** Four of
the five new expectations fail against the file as it was and pass after.
The pre-fix file was restored into a scratch directory created with
`mktemp -d`, not a bare shared name, which is PR #602's F46 heeded rather
than repeated.

### F48(b) — the live test's failure message said a 500 was the fix

**Moderate, same file, fixed here.** The live test asserted
`probed.status === 200` with the message "the events read now refuses an
unknown filter, which would be the fix". So on the day the route started
answering 500, the suite failed with a message telling the reader the
finding had been fixed. A test that detects drift and then misnames it
is worse than one that stays silent, because the failure text is what a
run acts on. It now distinguishes the three statuses that mean different
things: 5xx is the route down and the claim unchecked, 400 naming the
filter is the fix landed and working, 200 is the old inert state.

### F48(c) — a transcription tripwire whose slice could read the wrong handler

**Low, fixed here.** One of the two "transcribed:" tests sliced api.py
from the events route to the next `store.events(` and asserted the slice
did not contain "no such filter". `String.indexOf` returns -1 on a
missing marker, and `block.slice(0, -1)` is the whole rest of the file,
where the message route's own refusal would have satisfied the
assertion from a different handler entirely. Both ends are now asserted
to exist before the slice is used.

**Both transcription tripwires fired on this run, correctly, and are now
resolved.** Each asserted the *absence* of a fix so that the run finding
it present would be told to re-measure. HQ added it on 2026-10-26, both
fired, and each now asserts the new state. This is a tripwire doing its
job, so it is recorded as one rather than as a defect.
