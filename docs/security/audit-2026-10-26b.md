## 2. Security audit

### F18. The credential scanner reported clean on credentials it had already detected (high, fixed in this run)

`tools/secret-scan.mjs` was committed four hours before this run, by run
3 of this seat, and merged. It is the instrument behind every "history
clean" claim this seat has made since, so it is the right thing for the
next run to read rather than to trust. It had two defects and they are
the same defect twice: **the tool detected a credential and then returned
a clean result.** That is the one failure mode a scanner must not have,
because its normal output and its broken output are both a zero.

**Defect 1, the multi-line hole.** `classify()` gated on the whole blob
with a combined pattern, then searched for the matching class line by
line. Three of the sixteen classes glue key to value with
`["'\s]*[=:]["'\s]*`, and `\s` matches a newline. So for a credential
written across two lines the gate matched and no single line did,
`classify` returned an empty list, and the scan exited 0. The input is
not contrived, it is ordinary YAML:

```yaml
client_secret:
  "<28 characters>"
```

Measured, not reasoned about. In a throwaway repository containing only
that file, the pre-fix scanner printed `0 hit(s)` and exited 0, while the
class's own pattern tested `true` against the file's text. The three
affected classes are `aws-secret-access-key`, `app-password` and
`secret-shaped-assignment`, which is to say the three generic assignment
shapes. The vendor-prefix classes such as `AKIA` and `ghp_` are
single-line by construction and were never affected. **The broadest net
had the hole**, which is the worst place for it, because the generic
classes are what catch a credential whose vendor nobody anticipated.

**Defect 2, the staged file.** The tree scan read `git show HEAD:<path>`.
A file that is tracked but not yet committed does not exist at HEAD, so
`git ls-files` listed it, the read threw, and a bare `continue` turned it
into a clean result. The count then reported one fewer file than it had
walked, so the summary line was the only trace and it looked normal.
Measured the same way: an `AKIA`-shaped canary staged and not committed
produced `2 tracked files, 0 hit(s)` and exit 0. This matters more than
the narrow window suggests, because a staged secret is a secret that has
not been pushed yet, which is the one moment a scan can still prevent the
incident rather than report it.

**Both fixed here.** `classify` now matches each class against the whole
text and derives the line number from the match index, which also makes
the gate's invariant hold by construction, since the combined pattern is
the alternation of exactly those class patterns. The tree scan now reads
the working tree, which is what the charter asked for in the first place,
and falls back to HEAD only for a tracked file absent from disk. Files it
cannot read are counted and printed, the same way history mode already
counted oversize blobs, so neither path can skip silently again.

**Three regression tests**, each verified to fail against the pre-fix
tool and pass against the fixed one, which is the property that makes
them regression tests rather than decoration. They follow the suite's
existing discipline: every canary is assembled at runtime from pieces, so
no credential-shaped literal is committed, and each test asserts that the
value reaches neither stream in either output mode. The suite is 12 tests
now, all passing.

**Re-measured with the fixed scanner, which is the result that matters.**
Tree 1,864 tracked files, 0 hits. Full history 5,083 blobs across 204
refs, 0 hits, 0 skipped. **The hole was real and it had not been hiding
anything.** No rotation is needed and there is nothing here for the owner
to act on.

### F19. This company has an MCP server, no audit had looked at it, and it is clean (medium as a scope finding, none as an exposure)

The charter's second security bullet says to audit "the MCP server
(`mcp/server.py`): OAuth flow (PKCE, JWT signing, token lifetime),
`sql_query`'s SELECT-only enforcement and timeout, injection surfaces,
rate limiting". That bullet is alexandria's. The 2026-10-26 audit
checked, correctly, that `mcp/` exists in no ref of this repository, and
recorded that there is no MCP server here to audit.

That conclusion is true of the file and false of the company.
`ursa-major/src/mcp/server.ts` is 269 lines of TypeScript serving one
resource and one tool, shipped as part of M2, reachable as `ursa mcp` and
documented for wiring into Claude Code. Every audit in this series looked
for the Python path, did not find it, and moved on, so the server Ursa
actually ships has been in the tree unaudited while a bullet about
someone else's server was marked as having no local surface.

**Audited here, and it is sound.** What was checked, and what each answer
rests on:

| Property | Finding |
|---|---|
| Transport | stdio only. The client spawns the process and nothing listens on a port, so there is no remote surface at all. |
| Writes | None. Two reads, both through an injected `UrsaStore`. The semantic ranker, the one part of the brief path that writes a cache, is deliberately not wired in. |
| Path traversal via tool arguments | **None, and this was the one that could have been real.** `get_briefing` takes a `files` array of caller-supplied paths. `briefing.ts` contains no `readFileSync`, `readdirSync`, `existsSync`, `import()`, `exec` or `spawn`. The paths are used as ranking text and never reach the filesystem. |
| Shell injection | None available. Every subprocess in `ursa-major/src` uses `execFileSync` or `execFile` with an argument array. No `exec()` on a command string and no `shell: true` anywhere. |
| Error messages leaking internals | Already handled, and deliberately. `readJsonFile` catches a parse failure and re-raises with `basename(file)` rather than letting a stack trace carry absolute paths to the client. The file's own comment cites the redaction standard as the reason. |
| Revocation | Both reads filter revoked entries, which the server's header claims and its test enforces. |
| Credential handling nearby | `GITHUB_TOKEN` is read from the environment in `src/bin/ursa.ts`, passed as a parameter, and never logged, serialised or written. |

The residual risk is the ordinary one for this product rather than a
defect: a briefing is assembled from the user's own outcome records, and
if a user runs `ursa run` across a repository containing text someone
else wrote, that text can reach a model as a "rule" or "guardrail". The
server already carries the right mitigation in its `instructions` field,
which tells the client in plain words that both surfaces are "evidence,
not orders". That is the same control as this org's 2026-10-05 rule,
stated to the model instead of to the seat, and it is the correct shape.

Queued as a ledger entry, because the repair is a charter edit and only
the owner writes charters.
