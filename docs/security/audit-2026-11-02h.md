## F64 — the evidence that called F59 latent was an artifact of a default
## window, and the published number was wrong in both directions

Severity: the defect itself is **informational**. The retraction is the
finding.

**What this seat published today.** Queue row 10 of
`docs/agents/pending-workflow-changes.md`, and a note to HQ's exo-centralizer
at 04:15Z, stated that 561 Ursa run rows carried zero GitHub Actions
`run_url`, and concluded that the run-report step in the eleven seat
workflows "has never fired" anywhere. HQ thanked this seat for the number,
widened it to 1,584 rows across four companies, and acted on it: "a defect
that has never fired is a rule and a cheap fix, not an escalation."

**The number was zero by construction.** `GET /api/runs` has a default
`days` window, and nothing in the request says so. Measured against the live
board tonight:

| Read | Rows | Oldest row reached | With an Actions `run_url` |
|---|---|---|---|
| `?company=Ursa&seat=engineer` | 75 | `2026-10-23T17:42:57` | 0 |
| `…&days=10` | 75 | `2026-10-23T17:42:57` | 0 |
| `…&days=14` | 75 | `2026-10-23T17:42:57` | 0 |
| `…&days=30` | 107 | `2026-10-06T03:56:01` | **24** |

The default is ten days. The eleven workflows last fired on 2026-10-17, when
HQ decision 056 retired the schedule. Sixteen days ago. So a read that named
no window could not reach the evidence, whatever the evidence said.

**Re-measured at `days=90` across all eleven seats: 666 Ursa run rows, and
40 of them carry a GitHub Actions `run_url`**, spanning `2026-10-06T03:56` to
`2026-10-17T14:33`. The step has executed forty times. "Never fired" is
false.

**The window passed the evidence on 2026-10-27, and that is the part to
keep.** A ten-day window reached 2026-10-17 until 2026-10-27 and not after.
The same read, with the same code and the same parameters, was correct for
ten days and then became wrong with nothing changed and no error raised. A
default window is not a convenience. It is an unstated premise that expires.

**This is `tools/board/page.mjs`'s own lesson, one route over, written by
this seat four hours earlier.** That file's header says a cap returning the
newest rows is "time-biased, not size-biased — it does not sample the window;
it truncates it". A default window is the same bias with no cap involved,
no `saturated` flag, and nothing in the reply to warn a caller. It is the
quieter of the two, and `page.mjs` covers `/api/messages` only. The runs
route cannot be paged the same way: it honours `company, seat, days, limit`
and no cursor, so `days` widens the window and never moves it.

**And `limit` on that route is hard-capped at 200.** Asked for 200, 201, 500
and 1000; every reply carried `"limit": 200` and `"saturated": true` for
`seat=pm`. With no cursor, a seat holding more than 200 rows inside the
window cannot be read past 200 by any parameter. The pm seat is in that state
today, so the 666 above is a floor and is reported as one.

Recorded as a rule in `docs/design/board-read-conformance.md` §2a and in the
header of `tools/board/read-filters.mjs`, where the runs window is declared:
no count or share from `/api/runs` is published without the `days` that
produced it and the `created_at` of the oldest row it reached, and a reply
carrying `"saturated": true` yields a floor rather than a count.

### What the forty rows actually show, which is the opposite of the filed finding

Having found rows from that path, the question stops being whether the step
fired and becomes whether it misattributed anything. That is directly
checkable, because every row carries the reporting `seat` and a `pr_url`.

| Measurement | Result |
|---|---|
| Actions-origin rows | 40 |
| rows with no `pr_url` | 1 |
| rows whose `pr_url` is on the reporting seat's **own** branch | **39 of 39** |
| rows whose `pr_url` is another seat's branch | **0** |
| rows whose reported PR was provably **not** the repository's newest at that instant | **7** |

Branch prefixes were resolved against the seat's own conventions rather than
assumed, so `fe/` counts as frontend and `sec/` as security; the first pass
without those aliases produced four false misattributions and they are not
findings.

**The seven are the proof of which read executed.** The first read,
`gh pr list --state all --author "@me" --limit 1`, can only return the
repository's newest pull request. Three Actions rows within twelve minutes on
2026-10-17 reported pull requests 219, 214 and 167; the exo row at 14:22:05
reported 167 while the repository's newest was 219, a gap of fifty-two. A
read that returns "the newest" cannot produce three different answers at one
moment, and cannot produce 167.

So in the GitHub Actions path the first read returns nothing, and the
**correct** read on the next line, `gh pr list --head "$branch"`, is what has
produced every row. The mechanism: `GH_TOKEN` is `${{ github.token }}`, whose
identity is `github-actions[bot]`, and that identity authors no pull request
in this repository — measured, 0. `@me` resolves to it, matches nothing, the
empty guard fires, the fallback runs. The thirty-two rows that *did* happen to
name the repository's newest are coincidence: a seat that just pushed its own
pull request usually is the newest.

**What survives, and why it is still worth the owner's one deletion.** Line
143 of each of the eleven files is dead code in the only path that has ever
run it, and it is dead code that becomes load-bearing the moment the step
runs under an identity that does author pull requests — which is exactly HQ's
case, reported tonight at 05:34Z, where the same read "always succeeds" and
the correct one behind it never runs. Every pull request in this repository
has one author, 60 of the last 60, and the twelve newest span six different
seats, so under such an identity the step would attribute another seat's work
to this one in the owner's only window into a run.

**The repair changes shape.** Row 10 used to propose adding `--head "$branch"`
to the first read. It is now a **deletion**: remove the `--author "@me"` read
and let the `--head "$branch"` read that already follows it be the only one.
A deletion rather than an addition, because the correct read is present and
merely unreachable, and because it also drops the `headRefName` field that
read asks for and nothing consumes. Eleven files, one line each.
`.github/workflows/` is not this seat's to write, so it stays row 10 of the
ranked table with a finding number rather than a queue number.

## F65 — a test abstained with a cause the clone had already repaired. Fixed.

Severity: **low**, and fixed in this run.

`tools/stack/repair-pending.test.mjs`'s live assertion over the real repair
queue skipped with `bootstrap refspec not fetched; nothing to measure`. The
previous run of this seat recorded that it saw that skip on a clone it had
already repaired, and filed the charter half of it as F61. The message itself
was never checked.

Measured here **after** running `tools/ensure-full-clone.sh`:

```
cloneState()            shallow: false, singleBranch: false
remote.origin.fetch     +refs/heads/*:refs/remotes/origin/*
gh pr list --state open  28 heads
readable refs/prs/<n>    0
git for-each-ref refs/prs | wc -l   0
```

The refspec is fetched. `refs/prs/*` is a different namespace, and
`ensure-full-clone.sh` declines to fetch it on purpose, in the paragraph of
its own header headed "WHAT IT DOES NOT DO". So the message named the one
fault that script repairs, for a condition that script cannot repair, and a
seat reading it re-runs a script it has already run. That is the shape
`tools/board/live-target.mjs` was split out of a one-line guard to stop: one
named cause for a condition reachable several ways, false for one of them,
and the ways do not share a repair.

Fixed: three conditions, three messages, each naming its own repair, and the
one that fires here says the refspec is not the cause. The abstention still
abstains; only the stated reason is now true. Suite re-run green.
