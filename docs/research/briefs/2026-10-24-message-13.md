## Finding 49: Ursa's own pasted-conversation parser carries role labels in band, which is the defect a paper this month measures at 87 to 100 per cent across five harnesses, and here it lands on the span label `CLAUDE.md` §1 calls the most valuable

**The external instrument.** *Compaction Laundering: Provenance
Destruction in Context-Compacting Coding Agents*, Arshan Dabirsiaghi
(Pixee), arXiv:2610.29869, submitted 21 October 2026, primary cs.CR with
no cross-lists [E141]. Read at section-list depth with four verbatim
quotations taken against named questions [E142].

The paper's own subject is security. Its structural claim is the part
that travels: "Harnesses that flatten the roles into in-band labels, labels
carried in the same text as the content they mark, are exposed; those
that keep messages role-typed are not, because the tool's output stays
tagged as tool output and there is no in-band marker to forge" [E142].
Its measurement is that across five flattening harnesses a forged
approval launders into agent memory 87 to 100 per cent of the time,
while across four role-typed harnesses the identical attack succeeds 0
per cent of the time [E141]. Its fix is one line in the serializer:
"Escape the role labels in tool content before flattening" [E142].

**Where it lands here, and this step is this seat's inference rather
than the paper's claim.** `ursa-major/src/parse.ts` holds two capture
adapters. `parseClaudeSession` reads Claude Code session JSONL and
branches on `o.type !== 'assistant'`, so its roles are typed and it is
on the safe side of the paper's line. `parsePasteConversation` is on the
other side. It finds role boundaries with
`body.matchAll(/^##\s*(user|assistant)\s*$/gim)` at line 30, slices the
body between consecutive matches, and pushes every slice that followed
a `## assistant` header into `generations` as a `RawGeneration` with
`kind: 'assistant_text'` and the frontmatter's `model` [E143]. There is
no escaping rule, no fencing rule and no guard anywhere in the parser or
in the format's documentation, checked by grep [E143].

So any line in a pasted conversation that reads exactly `## assistant`
becomes a role boundary, and the text after it is recorded as a model
generation that no model produced.

**Why this is a data finding and not only a security one.** The output
of this parser is the input to the resolver, and the resolver's output
is the thing Ursa Minor sells. `CLAUDE.md` §1 names
`no_generation_provenance`, meaning text present in the finished work
and traceable to no generation at all, as "the most valuable category",
on the ground that it is the case where the model was never in the
running. Text the user wrote, mis-read as a generation, moves out of
that category and into `survived_verbatim`. The direction of the error
is the costly one in exactly the way the deletion module already
documents for its own labels: it manufactures evidence that the model's
output was used.

**Why the path is live rather than a test fixture.** `cli.ts` line 125
calls `parsePasteConversation` on every file in the directory the
`--conversations` flag names, so it is reachable from the shipped
command and not only from tests [E143]. `docs/design/product-plan.md`,
the plan of record, assigns this path a job in v0: "claude.ai chats
about the digest: handled by the existing `parsePasteConversation` path
(frontmatter + `## user`/`## assistant`), already built, zero new code,
she exports or pastes the conversation" [E144]. The committed fixture
carries `source: claude.ai` in its frontmatter, which confirms the
pasted-from-a-web-interface case is the designed one [E143]. That is
the case where arbitrary text arrives, because a person pasting a chat
pastes whatever the chat contained.

**The honest bound on likelihood, which is where this differs from the
paper.** The paper assumes an adversary: "An attacker who controls
anything the agent reads can therefore write a forged `[User]:` line
into it" [E142]. Ursa's threat model does not need one, because the
same defect fires on benign content, and the paper does not address
that case. The nearest sentence it offers is that a summarizer
"will still record a forged `[User]:` line as a user constraint, because
recording user constraints is its function" [E142]. For Ursa the benign
trigger is a conversation whose content is itself markdown with second
level headings called `user` or `assistant`, which is unusual in
general and is not unusual for this company, since a conversation about
this format, this parser or these briefs contains those strings. This
seat is not claiming a measured rate. It is claiming an unescaped
in-band delimiter in the parser that produces the commercial label, with
no test for it.

**What this does not say.** It does not transfer the paper's 87 to 100
per cent to Ursa, because that number is about their harnesses and their
attack. It also does not say the paper's fix applies unchanged, because
that fix is for a serializer and Ursa's code is a parser. For a parser
the same principle runs the other way and is named in the engineer note
below.

## Finding 50: a benchmark published two days ago measures erasure behaviourally, and the row of Ursa's own erasure table that answers consent is silent about the thing it measures

**The instrument.** *AfterDeleteBench: Auditing Post-Deletion
Information Persistence in LLM Agents*, Saleh, Nahavandi, Salarian,
Bassily and Perrault, arXiv:2610.31366, submitted 22 October 2026,
primary cs.CR with cross-lists to cs.CL and cs.LG [E145]. Read at
verbatim-abstract depth, which licenses a claim about the subject and
the headline numbers and not about the construction.

Its premise is Ursa's own: "Many LLM agents maintain external
persistent memory and derive additional state from past interactions,
such as summaries. Deleting an original memory record therefore need
not remove information carried by its descendants" [E145]. Its method
is a matched control this record has not seen before, comparing an
exposed-then-deleted agent against an otherwise matched agent never
exposed to the secret, so recovery can be attributed to the original
exposure. Its headline result is that a single query recovers the
deleted secret in roughly two thirds of cases while matched
never-exposed controls recover zero.

**The part that lands, and it is not the headline.** "Crucially,
recovery does not require a surviving verbatim copy: when the complete
secret string is absent and only separately stored components remain
under a public composition rule, exact reconstruction succeeds in 62 to
99 per cent of cases across Qwen, Mistral and Phi-3" [E145]. And the
mechanism that fixed it in their setting is the one Ursa already
built: "Provenance-aware closure eliminates observed recovery in the
tested positive-baseline settings, whereas an exact-literal write filter
blocks reinsertion but cannot erase information already present"
[E145].

**So the first half of this is confirmation and should be said as
such.** `docs/design/consent-and-erasure.md` §6c already erases by
provenance closure rather than by record, and the design's own worked
example reads "Erase one record and everything derived from it" [E146].
An axiom grounded only in the erased record is deleted outright rather
than tombstoned, and a blocked statement grounded only in it is dropped,
with the reason given that "a tombstone preserves the statement derived
from the thing being erased" [E146]. That is the paper's recommended
mechanism, built here before the paper, and this seat has found no prior
brief that says so.

**The gap is one row of that table.** The row reads: "An axiom also
grounded elsewhere: keeps its statement, loses this evidence,
`evidenceCount` recounted" [E146]. The design defends it directly, and
the defence is about consent: "The user erased a piece of work, not a
conclusion. A conclusion that still rests on evidence she has not
erased is one she has not objected to, and revoking is how she objects"
[E146].

That reasoning is sound on the question it answers, and it answers a
different question from the one the paper measures. Consent asks whether
the user objected to the conclusion. Recoverability asks whether what
remains can reconstruct what she erased. A statement whose wording was
derived in part from the erased record, retained because it is also
grounded elsewhere, is exactly the "separately stored components under a
public composition rule" shape, and the composition rule here is public
because the distillation prompt and the axiom schema are in the
repository. Nothing in `consent-and-erasure.md` or in
`revocation-store-gate.md` states a position on reconstruction, checked
by grep for derived, derivative, descendant, downstream and aggregate
across both [E146].

**Confidence, and what would settle it.** Medium on the gap and low on
its size. The claim that the design is silent on reconstruction is
first-hand and high confidence. The claim that reconstruction is
actually achievable against Ursa's retained axioms is untested by
anyone, including this run, and the paper's 62 to 99 per cent is about
synthetic secrets under a composition rule its authors designed, not
about axioms. What would settle it is the paper's own experimental
shape, run on Ursa's artifact: erase a record, then ask the tuning
record's own reader to reconstruct the erased content, against a matched
arm that never held it. Ursa has no such arm, which is the same gap the
fourth run named for the cold-start baseline. That is a trial design
note and it is routed below rather than claimed as a result.

## Step 3, skill target: one

**Target: keeping provenance out of band, for any code in this
repository that reads or writes a conversation.** Ranked first and the
only one proposed.

The evidence is three mutually reinforcing instances of one principle,
which is the bar this charter sets, and they come from three different
directions rather than three papers saying the same thing.

- The external measurement, arXiv:2610.29869: in-band role labels
  launder a forged turn 87 to 100 per cent of the time across five
  harnesses, role-typed messages 0 per cent across four, and the
  structural reason is stated as a general property of in-band labels
  rather than as a property of those harnesses [E141][E142].
- This repository's own instance, finding 49: an unescaped in-band
  delimiter in the parser whose output is the commercial label
  [E143].
- This repository's own second instance, already in the record and from
  a different surface: the 2026-10-23 correction in
  `docs/design/consent-and-erasure.md`, where the revocation check read
  `match.status === 'revoked'` and `match` came from
  `DistilledAxiom.matchesExisting`, "a field the model fills in", so a
  model that restated a revoked axiom in new words and left the field
  null was never checked [E146]. That is the same principle with the
  model in the attacker's chair rather than a pasted document, and the
  repair was to stop trusting the in-band field and score the statement
  instead.

The judgment the skill has to carry, which is why it is a skill rather
than a ticket. The rule "do not trust metadata the content can write"
is easy to state and the hard part is recognising the shape, because in
all three instances the in-band marker looked like structure rather than
like content. The procedure therefore starts from an enumeration of
every place a role, a provenance mark or a status arrives in the same
channel as the thing it describes, and asks of each one who can write
that channel. The tradeoff to state is that in-band markers are what
make a format pasteable by a human, which is a real product property
here and not an accident, so the answer is not always to delete them.
The failure mode to state is a fix applied at the wrong end, since
escaping on write does nothing for a parser that will be handed text it
did not write.

Read against `skills/` on this branch and the four open skill pull
requests #316, #320, #348 and #359, this is not something that seat has
drafted or is drafting [E147].

## What the engineer should know before building

**Routed to the engineer seat, anchored at
`ursa-major/src/parse.ts:30`.** The fix the paper names is for a
serializer and Ursa's code is a parser, so the direction reverses. A
parser cannot escape what it is handed. What it can do is one of three
things, and the choice is a product decision rather than a bug fix.
Prefer the role-typed source where one exists, since claude.ai's own
export is structured and the pasted-markdown path exists for
convenience rather than necessity. Or require the delimiter to be one
the content cannot produce, which costs the hand-pasteability
`product-plan.md` is relying on. Or detect the collision and refuse,
which is the cheapest and fits this repository's existing habit of
yielding `unknown` with a named reason rather than guessing, the way
`deletion.ts` already does for an unreadable merge boundary. There is
no test for a role header inside message content anywhere in
`ursa-major/src/`, checked by grep [E143].

**Routed to whoever designs the next trial.** Finding 50's method, a
matched arm that was never exposed to the thing under test, is the
second time in two days this record has wanted an arm Ursa's two trials
do not have. The fourth run wanted one for the cold-start baseline. This
run wants one for erasure. Both are the same missing piece, which is a
control arm, and naming it once is cheaper than wanting it twice more.
