## What is RISING

### 1. An independent audit of what a git repository can supply about AI provenance, and it rules **absent** the exact row Ursa Minor sells (high confidence, full text read)

`arXiv:2610.28655`, *What Git Does Not Record: Provenance Legibility in
Two AI-Assisted Research Repositories*, Wu, Huang and Geng, submitted
9 October 2026, cs.DL primary with cs.AI and cs.LG [E1]. Two
single-investigator repositories by one author, 466 and 103 commits,
audited at a fixed census commit per project, with four measurement
scripts and a fifth that checks every number printed in the paper
against them.

Its Table 3 takes the provenance fields an AI-disclosure statement would
need and gives each a verdict against what a normally-kept repository
supplies. Four rows matter here, quoted from the table:

- **`Accepted unchanged`**, whose best available evidence the table
  gives as "not distinguishable from authored text", verdict **Absent**. The paper's own gloss: "a repository records only the state
  after the human decided, storing an accepted suggestion and a
  hand-written line identically."
- **`AI involvement`**, evidence `Co-Authored-By` when written, verdict
  **Misleading**.
- **`Model identity`**, evidence "free text inside the same trailer",
  verdict **Partial, tool-dependent**.
- **`Intermediate states`**, "discarded between commits", verdict
  **Absent**.

Read against `CLAUDE.md` §1, the first row is `survived_verbatim`
against `no_generation_provenance`, which is the distinction the whole
commercial artifact is built on, and the third row is
`generation.model`, which is what the cross-model comparison in
`CLAUDE.md` §4 groups by. **An outside party with a published method
has now measured that both are unrecoverable from a repository read
after the fact.**

The numbers behind those verdicts, all from the full text:

- `Co-Authored-By` is one of **three** keys naming an AI system in the
  larger repository. It covers 66 commits, `Made-with` covers 55 naming
  a different tool, `Claude-Session` 2, and no commit carries both of
  the first two, so the keys "divide the record rather than corroborate
  it". An audit keying only on `Co-Authored-By` misses **45.5%** of the
  disclosures that repository holds.
- Against the repository's own within-repository proxy, the trailer's
  sensitivity is **2.6%** in one project and **33.3%** in the other.
  Thirty-nine commits revise the file the project kept to hold the
  agent's working notes and one carries the trailer.
- The repository-level disclosure rate steps from **2.7% to 17.7%**
  across a boundary the authors located by inspecting the series rather
  than specifying it in advance, and they say so.
- Across 66 disclosing trailers the identity string takes **6 distinct
  values for at most four models**, of which "two differ only by a
  context-window suffix and denote the same model" and one is a bare
  vendor name.
- Of the lines ever committed to the narrative trace artifact, **21.8%**
  are visible at the current revision, against 85.6% for the
  prescriptive one. Counted by revision the gap nearly closes, 15 of 41
  against 18 of 41, which is the authors declining to attribute the
  contrast to the trace format.

**Why this is the most useful outside paper this record has carried, and
it is not because it agrees with us.** The paper's §8 derives six
requirements for in-situ capture from the gaps it measured. Three of
them are decisions already made in this repository, and reading them
from outside is what makes them legible as decisions rather than as
implementation detail:

- **Requirement 1, "record the accept event, not just the result."**
  That is `pairfinder.ts`: the generated commit and the first human
  commit that touched its output, which is an accept event reconstructed
  from the only two states a repository holds. The paper says a
  repository cannot supply it. Ursa supplies it by owning the launch and
  bounding the pair, not by reading the repository afterwards. This is
  the clearest statement of Ursa Minor's actual moat anywhere in this
  record and it comes from outside the company.
- **Requirement 2, "separate the involvement field from the
  tool-identity field, and name both," and "the involvement field needs
  a defined value for 'not recorded' so silence is not read as
  absence."** That is, line for line, the `ApparatusObservability` type
  the engineer shipped today in `ursa-major/src/apparatus.ts`, including
  the `unobservable` value and the reason it exists. It was published
  fifteen days before he wrote it and neither of us had read it. The
  engineer asked to be checked on that decision. It is not merely
  defensible, it is the published requirement.
- **Requirement 5, "bind records to history rather than to paths."**
  This one Ursa does not satisfy, and it is finding 2.

Confidence: high. Full text read, including the method section stating
the three query forms and the threats section stating the single-coder
limitation and the two-repository scope. The authors claim existence and
not generality and say so repeatedly, so this brief claims the same.

### 2. Measured first-hand: a file rename makes the shipped durability walk report intact text as decayed (high confidence, module executed)

`ursa-major/src/lifespan.ts:97` documents, deliberately, that `--follow`
is not used: "it would make a rename look like continuity of content,
and the question here is about the text, not about the path it lives
at." `docs/design/span-lifespan.md:322` states the same tradeoff. The
reasoning is sound and this is not an argument against the choice.

The problem is that the code implements a third outcome neither side of
that tradeoff chose. `revisionsAfter` runs
`git log <finalSha>..HEAD -- <path>`, and a path-limited log **does**
return the commit that renamed the path away, because that commit
deletes the old path. `blobAt` then fails on it, and
`lifespan.ts:220` states what happens next: "A null blob means this
revision deleted the file. That is a real death for every unit in it,
not a reason to skip the revision."

Measured, by building a repository with an agent commit, an owner commit
closing the episode, a `git mv`, and one further commit, then calling
the shipped `revisionsAfter` and `traceFile` on it with `tsx` [E9]:

```
revisions revisionsAfter() returned: 1
  [{"sha":"0b34c91…","subject":"owner: move the doc into docs"}]
lifespan: { "unitsTraced": 5, "unitsSurviving": 0,
            "survivingChars": 0, "decayedChars": 421,
            "intactRevisions": 0, "intactSeconds": 0,
            "diedAtSha": "0b34c91…", "liveAtTip": false,
            "fate": "decayed", "basis": null, "skipped": null }

is the span text still at the tip, at the new path? true
```

Every unit dies at the rename. The text is intact at the tip. The
docstring's stated worry was a rename read as false continuity. The
implemented behaviour is a rename read as total destruction, which is
the opposite error and the one this module exists to prevent in reverse.
`annotateDurability` feeds `decayedChars` into `decayRate`, which
`lifespan.ts:152` describes as "a conservative floor on decay rather
than a point estimate". A rename removes that guarantee: the floor
becomes an overstatement.

**How much this has already cost: nothing, so far, and that is reported
rather than assumed.** Across the sixteen records this run resolved over
Ursa's own history, 269 spans carry a death commit, and **zero** of
those commits renamed or deleted the span's own path [E10]. `origin/main`
holds 11 renames in 1,089 commits, 5 of them under `ursa-major/src`, and
none fell inside a traced window. So the defect is latent here and the
paper measures it as having fired in one of the two repositories it
audited, where a path-limited log returned 7 revisions against
`--follow`'s 41 and placed the artifact's apparent start 228 days late,
with, in the paper's words, "no sign it was partial."

For the engineer, and stated as the three options rather than as a
prescription, because the choice is his: detect the rename and mark the
span `untested` from that revision rather than dead, or follow the
rename and keep the existing text-identity test at the new path, which
is not the same thing as trusting `--follow`'s notion of continuity, or
keep the behaviour and name it in `SpanLifespan` with a flag a buyer can
filter on. What is not an option is the current state, where a rename
and a deletion produce identical bytes in the record.

### 4. A controlled audit says a personal-memory pipeline can be worse than handing over the raw history (high confidence on the abstract, which is where this claim lives)

`arXiv:2610.02764`, *A Controlled Audit of Personal AI Memory for Rating
Prediction*, Gupta, submitted 2 October 2026, cs.LG [E4]. Permutes each
user's historical ratings while preserving the rating distribution, item
support and metadata, which isolates whether a personal AI uses
item-rating associations or only the user's rating tendencies. On Coat,
a Mem0 pipeline **increases** user-macro mean absolute error relative to
full history by 0.084 and 0.149 for two readers, both family-adjusted
bootstrap intervals excluding zero. A history-only ridge reader
outperforms one LLM reader in both domains.

Why Ursa Major should care more than the domain suggests. Major's
proposition is a derived, portable profile: "from the first message on
any AI, it already knows how you like to be answered" (`CLAUDE.md` §3).
This paper's control is the comparison Major has never run against
itself, which is not "profile against nothing" but **profile against
simply handing the model the history**. On one of two domains, the
derived layer lost to its own input. That does not refute Major, whose
claim is about portability across vendors rather than about rating
accuracy, and the paper is rating prediction rather than preference
expression. It does mean the baseline belongs in the design: a profile
that loses to the transcript it was derived from is a worse product and
a worse thing to sell as consented signal. Confidence is high on what
the paper measured and this seat makes no claim about its full text.

### 5. A four-state validity lattice for memory invalidation, with a provenance graph (medium confidence, abstract depth)

`arXiv:2610.05732`, *PACMI: Provenance-Aware Cascading Memory
Invalidation for Long-Term LLM Agents*, Wang et al., submitted 5 October
2026, cs.LG with cs.IR [E5]. Represents memories and new evidence in a
provenance graph with typed dependency edges, assigns records to a
four-state validity lattice, and propagates validity changes to
dependent memories. Diagnostic benchmark of 100 cases and 300 queries
across five domains. The premise checker reaches perfect precision and
recall on a controlled query distribution. Removing cascading
propagation moves final-answer errors from 3 to 11, and the authors say
that paired difference does not reach significance.

This is the architecture `CLAUDE.md` §3's edit-and-revoke promise needs
and does not yet have. Major promises the user can edit or delete what
was inferred about them. An inference that was derived from a deleted
memory is a dependent record, and nothing in this repository propagates
that. Two of the three prior revocation findings in this record treat
revocation as a two-state problem. A four-state lattice with typed edges
is the published alternative, and it is the first paper in this record
that makes propagation rather than deletion the object.

### 6. Pairwise disagreement is not identifiable from a binary channel, and the thing that identifies it is what Ursa already collects (high confidence on the abstract)

`arXiv:2610.20450`, *What Does Disagreement Mean? A Semantic
Identifiability Frontier for Pairwise Preference Learning*, Saravanan,
Salla and Kota, submitted 14 October 2026, cs.GT with cs.LG [E6]. Proves
an exact semantic fiber theorem: under an anonymous binary comparison
channel the aggregate directional preference is point-identified, while
persistent disagreement and non-binary mass vary over an explicit
feasible region compatible with the same binary law. **Same-annotator
repeats identify persistent disagreement through a covariance identity,
and abstention-enabled feedback identifies non-binary mass.**

This is an argument for Ursa Minor from an unexpected direction, and it
is about the trajectory metadata rather than the span labels.
`CLAUDE.md` §1 wraps each record in "corrections that recurred" and "the
point where the goal itself shifted mid-task". A recurring correction
from the same user on the same task **is** a same-annotator repeat, and
an abandoned task **is** an abstention. So the two quantities this paper
proves unidentifiable from the preference-pair market's standard channel
are identifiable from the shape of signal Ursa collects, by this
paper's own identification result. `CLAUDE.md` §5 says Minor "is not
selling more preference pairs into a market that already has them." This
is the cleanest formal statement of why that sentence is true, and it
should be read before the next pitch is written rather than after.

### 7. The apparatus confound runs below the client and the cap, down to the sampler (medium confidence, abstract depth)

`arXiv:2610.15570`, *Truncation Samplers Are Nested: Comparing Decoding
Rules Is a Measurement Problem*, Khanbayov and Kurban, submitted
11 October 2026, cs.LG with cs.CV [E7]. Almost every deployed truncation
rule keeps a prefix of the probability-sorted vocabulary, so any two are
nested at every step, which yields a closed-form separation certificate.
On six open-weight models over four benchmarks the certificate is **at
least 0.998 for every hyperparameter grid tested**, so a bound alone
rarely settles a comparison. Resolving a one-point difference needs 8 to
32 samples per prompt on three benchmarks and about 210 on AIME 2025,
and at the upper confidence bound of the between-prompt component AIME
2025 "cannot be resolved at any sample count."

For the apparatus field this is the next layer down. `Apparatus` today
carries the client, the cap, the output tokens and the stop reason. It
does not carry the sampler or its parameters, and this paper's result is
that two samplers are nearly unbounded apart on the certificate. The
field does not need to grow today, because every generation this build
resolves is `unobservable` anyway. It needs to grow before the first
transcript path lands, which is the same timing argument the engineer
acted on, pointed one level deeper.

**One proposal, and it is a four-line amendment to this seat's own
charter.** The written listing set and the rule that maintains it are
both on this branch and both working: the set said cs.LG, cs.CV and
cs.ET had never been opened, and two of the three were opened this run
because the file said so. That part needs no change beyond recording
what was read.

The rule that grows the set is the defect. It says to read "the
categories the cited papers of your last several briefs were actually
filed under" and "any category that has produced a cited finding and
that this seat has never opened as a listing." Both clauses derive the
set from the record's own citation history, so **the set can only ever
grow toward categories the record has already touched**, which is
exactly the blind spot the rule was written to close.

The evidence is a pattern with three instances, each more expensive than
the last:

  three runs after the rule landed. Opened at 5,108 of 5,108 and
  produced three absent papers.

  seat has written [E8]. It could never have qualified. This run's lead
  finding is a cs.DL paper, and it is the paper that measures the
  substrate Ursa Minor's whole artifact is built on.

verify it by opening one file.

It is a proposal. The owner's merge is the promotion.
