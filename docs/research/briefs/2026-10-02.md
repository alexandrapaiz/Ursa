### 1. Multi-agent failure now has a measured taxonomy, and Ursa's own operating record matches it mode for mode (high confidence)

This is the owner's first standing coverage area
(multi-agent systems, agentic design), reported **uncovered** by the
runs of 2026-09-29 and partially covered on 2026-09-30. It is covered
now, and the finding points inward.

**[E1]** classifies multi-agent LLM failure into 14 modes in three
categories — "(i) system design issues, (ii) inter-agent misalignment,
and (iii) task verification" — validated at "kappa = 0.88", and
measures a "41% to 86.7% failure rate on 7 state-of-the-art (SOTA)
open-source MAS". The per-mode prevalences are the useful part, and the
three largest are **step repetition (15.7%)**, **reasoning-action
mismatch (13.2%)** and **unaware of termination (12.4%)**.

Ursa is an eleven-seat multi-agent system (eleven `prompts/*-agent.md`
charters, eleven `agent-*.yml` workflows). Set its verified record
against those modes:

| [E1] mode | Prevalence | Ursa's instance (all verified this run) |
|---|---|---|
| FM-1.3 step repetition | 15.7% | `prompts/research-agent.md` exists in **three** versions (`main`, #19, #48); `docs/sprints/pending.md` in **four** (#37, #45, #60, #67); the skill library is a **three-deep** unmerged stack (#14 → #50 → #64) |
| FM-1.5 unaware of termination | 12.4% | **48 PRs open**, and the last merge of anything but a standup, a lessons sync or board wiring is PR #9 on 2026-09-21 — eleven days (#67) |
| FM-3.2/3.3 verification failures | 8.2% / 9.1% | "Every PR checked this run is green CI, unreviewed" (#67). CI verifies; nothing adjudicates |
| FM-2.5 ignored input | 1.9% | Seven days of briefs and **no seat has cited one** (#48, and see finding 5) |

**The conclusion that is actually new.** The merge jam is already filed
and PM-owned (#45, #60, #67, `docs/sprints/pending.md`), and this brief
does not re-file it. What the literature adds is a **diagnosis**: the
jam is not a backlog of effort, it is a **missing termination
condition** — [E1]'s FM-1.5, the third most common failure mode in the
field. Every Ursa seat's charter specifies how to open a pull request
and **no charter specifies the condition under which work is
considered finished**. Under that specification, 48 open PRs is not a
malfunction, it is the system doing exactly what it was told. More
merging effort treats a symptom; a termination condition is the fix,
and it belongs to the PM and the owner rather than to this seat.

**[E2]**, posted 2026-09-01 and inside the field's current window,
sharpens the warning for anyone tempted to read the jam as bad luck:
"Safe agents can fail together", because these systems "move
information and authority across organisational boundaries" where
isolated checks cannot see. Its caution is worth quoting at Ursa
directly — "Without an execution-level view, a multi-agent setting can
easily be mistaken for evidence of a genuinely multi-agent security
effect" — and it names "path closure and recovery" as the open problem.
Path closure is the merge. Ursa has no closure.

### 2. Personalization's frontier moved to preferences that contradict themselves over time (high confidence)

**[E3]** (2026-09-11) is the most directly useful external paper this
seat has found for Ursa's product. It introduces ReaLMem, "the first
benchmark built from authentic multi-year personal visual archives",
and proposes "ChronoProfiler, a temporal-weighting profiling module
that computes temporal stability scores for user attributes and applies
them as a salience prior, **resolving conflicts among temporally
inconsistent preferences**". Its headline result is that "predictive
personalization" is "a consistent ceiling".

This matters twice over.

**For the record (O1 KR1.2, and PR #57, open).** `CLAUDE.md` §1 already
names the time dimension — "not just *what* survived but *how long*" —
and the hardest unowned problem in it is **the point where the goal
itself shifted mid-task**, which the same section lists as trajectory
metadata. A goal shift and a correction are the same edit seen from two
distances, and [E3] is the first external work this seat has read that
attacks that exact ambiguity with a measured instrument rather than a
heuristic. PR #57 is implementing the time dimension right now, and it
should know this vocabulary exists before it finalizes field names.

**For the pitch (O2).** "Predictive personalization as a consistent
ceiling" is an independent, benchmarked statement that the thing Ursa
Major claims to do is the thing the field cannot yet do. That is a
stronger sentence than any Ursa has written about itself, and it comes
from outside.

### 3. Text-only user memory measurably loses half the user (high confidence, uncomfortable)

This is the owner's third standing coverage area (multi-modal), and the
finding **cuts against** Ursa's current architecture, which is why it
is here.

**[E4]** measures what a text memory discards. A persistent user memory
"is almost always text — transcripts and captions retrieved by
similarity", which "serves the captionable half of a person ... but
discards the perceptual half no caption can hold: how a voice sounds,
how a face reads across age and lighting, how tired someone sounds."
Measured across five modalities, "a strong caption-based re-identifier
recovers as little as **0.11** of a dedicated encoder's recall,
collapsing toward chance on non-nameable signals." Its conclusion is a
split: "identity belongs in a parametric bank, facts in a text store."

Ursa's artifact is **entirely text spans**. The four span classes in
`CLAUDE.md` §1 classify characters of a finished work, and
`ursa-major/src/tuning/export.ts` emits a text block. On [E4]'s
evidence, that is a deliberate restriction to the captionable half, and
it is **defensible but currently undeclared**: Ursa's claim is about
*revealed preference in finished work*, not about who the user is
perceptually, and a text artifact is the honest carrier for a text
outcome. The risk is a buyer or a lab asking the multi-modal question
first and Ursa having no stated position. **Recommend one paragraph of
scope declaration**, not an architecture change. Cheaper now than in a
lab meeting.

*Date caveat:* [E4]'s abstract page reads 8 Jul 2026 while its
identifier is `2608.*`. The two disagree; the **date is treated as
uncertain** and the paper is cited as standing-coverage context, not as
an event inside this window.

### 4. The rubric verifier keeps compounding, and now has dedicated hacking infrastructure (medium-high confidence, confirms #48)

### 5. Portability's interchange formats carry provenance and not consent (high confidence, and it corrects #48)

**[E6]**, the Data Transfer Initiative's 2026-09-01 post, describes
portability progress as "inconsistent and very incomplete". Claude
supports memory import and export, Gemini "has rolled out guidance to
import such data", W3C and IETF work is named, and CDT's Kevin
Bankston is quoted — "Don't Let Perfect be the Enemy of Portable" —
with the remaining gap being **imports**.

**[E7]** is the first AI-memory interchange specification this seat has
opened directly. PAM is "an open specification — not a product, not a
service, not an API — that defines a vendor-neutral interchange format
for AI user memories", v1.0, and it **requires provenance fields**:
`platform`, `extraction_method`, `conversation_ref`. It does **not**
define a consent or revocation mechanism. It is also maintained by one
named individual under CC and Apache-2.0, and the page is advocacy by
the spec's own author.

Two consequences, one of them a correction.

- **Differentiation is narrower and sharper than Ursa has claimed.**
  Provenance is no longer Ursa's alone — an independent spec now
  mandates it. **Consent, revocation and erasure are not in any format
  this seat has read**, and `ursa-major` is building exactly that right
  now (PR #59, the consent gate). That, not provenance, is the
  defensible line. It is also the one that `CLAUDE.md`'s load-bearing
  constraints 2 and 3 already commit Ursa to.
- **#48's recommendation to drop a hedge was premature** (Corrections 2).
