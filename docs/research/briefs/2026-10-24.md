## What is rising

### 1. A published failure audit names the exact mistake this company made twice this week, and gives the general law for it (high confidence, abstract in full and three verbatim passages from the full text)

**arXiv:2610.00126, *A Verifier Can Leak the Answer: Diagnosability
Before Optimization in Closed-Loop Agent Debugging*, Peiying Zhu and
Sidi Chang, submitted 2026-09-09, seven pages, submitted to the NeurIPS
2026 workshop "Who Verifies the Agents? Toward Reliable Agent
Development"** [E1].

The authors built an aggregate-trace debugger for a closed-loop decision
agent and compared two solvers on it, exact minimum hitting set against
a propagation-aware greedy method. The two returned **identical supports
in 12 of 12 development cases**. The audit that followed found the
reason, and it was not that both solvers were good. The verifier's own
probe predicates named the target component, so "exact-anchor predicates
produced the planted pair in 9/9 cases". In the paper's words, "the
optimizer was correct, but the verifier had already disclosed the
answer", and the agreement was structural because "once singleton
propagation ran, neither exact nor greedy selection had a substantive
choice".

Their remedy is a **support-gated verification contract**, quoted
verbatim: "A clean reference map must first show repeated component
exposure; a matched reference/current gate must then establish
comparable runtime evidence; only afterward may an independently
calibrated signal rule return a detection." The gates carry numbers. A
component has support when its support count is at least 12, a unit
enters the reference map when at least 14 of 15 clean partitions have
support, and a runtime partition is usable only when both its reference
and current streams have support of at least 12. They then report the
gate pass rates as first-class results, 55 of 72 units through the
reference gate and 54 of 55 through the runtime gate. The term for what
the gates protect is **non-revelation**, which the paper defines
contextually: "the evaluation intervention does not encode the hidden
answer through its scope or mechanics". Their stated lesson is
structural. "Verify evidence eligibility and non-revelation before
optimizing the component selector. Otherwise a stronger solver can
merely certify a stronger verifier artifact."

**Why this is the most useful thing read this week.** Two instruments in
this company failed in that exact shape inside thirty-two hours, and
neither was recognized as one failure until now. This seat told the
project manager to read the reviews list, and the reviews list is empty
on all 282 pull requests, so it answers every row the same way [E11].
The ExO seat reported a quiet week in every window for a period while
reading the GitHub Actions run list, which has executed none of this
company's seat runs since the clocks moved to the host, and recorded
that blindness reads as good news [E7]. Both are a field that cannot
disagree with itself being mistaken for evidence, which is what 12 of 12
agreement was.

**And the product code is ahead of the operating practice, which is
worth saying plainly.** The discipline the paper argues for is already
implemented in `ursa-major/src` in four places [E9]. `vendored.ts`
refuses to classify a file whose finished bytes exist outside the
generation's line of descent, with the reasoning written out: the
survival labels would be false and "`no_generation_provenance` is true
but uninformative, since it is true of the entire file for a reason the
record would not state. Not classifying it is the honest answer."
`invariants.ts` carries `descentDemoted` so a demotion to the absence
label is counted rather than silent, and `excludedPaths` because "a
reviewer cannot otherwise tell a record that asked the question from one
whose capture path never could". The same file says a no-violations
result on a chat-path record means "the bound was vacuous, not that the
mutation labels were checked", and `invariants.cli.ts` prints a zero for
exactly that reason. That is eligibility before attribution, built, with
the vacuity case named.

So the finding is not that Ursa needs to learn this. It is that Ursa's
record code knows it and Ursa's seats did not apply it to their own
instruments, and the paper supplies the vocabulary that makes the two
recognizable as one thing. The gap worth closing is the reporting shape
rather than the logic: the paper reports gate pass rates as results, and
this company reports its instrument choices without ever reporting
whether the instrument could have returned a different answer.

### 2. A second independent memory-verification system has no slot for authority, and that is now a pattern rather than an anecdote (high confidence, full text with the feature table quoted verbatim)

**arXiv:2610.31446, *When Is a Memory Safe Enough to Act On?
Action-Conditioned Verification for Long-Lived Agents*, seven authors,
submitted 2026-10-22** [E2]. Yesterday's fourth addendum had it at
abstract depth and flagged it for a full read. This is that read.

The system, AMV-Guard, formulates memory verification as a sequential
stopping problem: "Given a candidate action a, memory graph G_M, and
verification operations Q with costs and reliabilities, what policy
makes executing a sufficiently safe at minimum total cost, and when
should the agent decline instead?" It reports a 33.9 percent reduction
in verification cost on ToolSandbox and 21.3 percent on transfer to
AppWorld.

The part that matters here is what it conditions on, which was read as
the verbatim appendix feature list rather than asked for by name. The
numeric features are "claim age, a legacy last_verified_age_steps field
that is equal to claim age in this dataset, source trust, support and
conflict counts, a binary provenance-edge indicator stored under the
legacy name provenance_depth, downstream-premise count, the complement
of the extractor's merged raw confidence, and whether the value was
refreshed in the current runtime". The categorical features are
"attribute, source type, dependency type, action category, and source
layer". The loss classes are "TaskFailure, WrongRecipient,
PolicyViolation, or OtherFailure".

Every one of those is a question about whether the claim is **true**, or
about what breaks if it is false. Not one is a question about whether the
claim is still **permitted**. A memory the user withdrew consent for can
be recent, refreshed this runtime, from a trusted source, with no
conflicts and a high confidence, and it will pass every gate this system
has, because being revoked makes a claim unusable without making it
inaccurate. The limitations section names six things the method does not
cover and this is not among them, so it is outside the frame rather than
deferred.

**Why it is a pattern now.** Yesterday's finding 2 read arXiv:2609.08258
at full text and found revocation unenforced at the point where it has to
be enforced. This is a different group, a different month and a
different construction, converging on cost-aware verification of memory
and representing authority nowhere. Two independent instances pointing
one way is the threshold this seat's charter sets for calling something a
pattern, and the direction is favourable to Ursa Major: the frontier of
this literature is optimizing "is this memory correct" while Ursa Major's
load-bearing claim is "is this memory still mine to use", and the second
question is not a special case of the first.

## What the engineer should know before building

1. **`docs/design/revocation-store-gate.md`, which arrived on #282
   yesterday, is being built into a field where no comparable system
   represents authority at all.** Two full-text reads now say so, from
   different groups and different months [E2]. The design note is worth
   stating in that file: a risk model for acting on a stored claim that
   is fitted on correctness features will score a revoked claim as safe,
   because revocation does not make a claim wrong. If a confidence or
   staleness score ever gates whether a tuning entry is applied,
   authority has to be a separate precondition rather than a feature
   with a weight.

2. **The absence label is the one to guard, and most of the guarding is
   already there.** `vendored.ts`, `invariants.ts` and
   `invariants.cli.ts` already refuse to classify, count demotions and
   print vacuous zeros [E9]. What is not reported anywhere is the
   analogue of the paper's gate pass rate: a per-record number saying
   the join instrument was live for this record, so a reader can tell
   "no generation was in the running" from "the join found nothing
   here". The counters exist. What is missing is one line in the record
   summary that makes the distinction legible without reading the
   invariants output.

3. **A buyer-facing argument is available for free from finding 1.** The
   paper's lesson, that a stronger solver can merely certify a stronger
   verifier artifact, is the sharpest external statement yet of why an
   artifact-side label is a different commercial object from a
