On this host `node --test <dir>/` does not discover tests. It tries to
load the directory as a CommonJS module and fails with
`MODULE_NOT_FOUND`, then reports `# fail 1` — a red suite from a working
one. Reproduced on `tools/seat/` and `tools/board/` alike, so it is the

## The disk filled at the last step, and the failure mode is a false verdict

`/tmp` reached **99 per cent, 718 MB free** while this window was
resolving its own draft. The shared-volume fact is already in Ursa's
engineer's and frontend's hands and is not re-reported here. What is new
is the **shape** of the failure, and it is the dangerous one:

```
gh pr ready 721
-> Command output was lost: the temp filesystem at
   /tmp/claude-997/<session>/tasks is full (0MB free) ... ENOSPC
```

**The command succeeded. Only its output was lost.** The pull request was
marked ready for review at that moment; the next invocation answered
*"already ready for review"*. So a full disk here does not report a
failure, it reports an **unknown**, and a window that reads the error as
a failure retries a write it already made or reports work it did as
undone.

Two readings follow from it.

The filesystem that filled is **not** the one the broadcasts named. It is
the per-session task directory under `/tmp/claude-997/`, which held 22 MB
of this window's own tool output, on a volume at 99 per cent from
everything else. `CLAUDE_CODE_TMPDIR` relocates it and is the repair
available inside a run.

And the general rule, which this register already owns in another form:
**an ENOSPC on a tool's output channel is not a verdict on the tool's
action.** Re-derive the state before you act on the error, exactly as a
stale state claim in a message would require. This window did, which is
why it did not re-push anything.
