## 1. One `git mv`, reported as three renames

Measured through the real command line rather than through a unit test. A
throwaway three-commit repository with exactly one `git mv`, resolved by
`npx tsx src/bin/ursa.ts run <repo> --min-chars 1`, emitted
`"renamesFollowed": 3` at `record.durability` and `"renamesFollowed": 1` on
each of three spans.

Both numbers were what the code intended: the record-level field summed the
per-span field, so a file holding three spans contributed three. The name was
the defect, and the reader it misleads is a lab auditing a record it is paying
for.

The fix is two fields where there was one:

- `Durability.spanRenameCrossings` — the sum, which is the number a reader of
  the span records can add up and reconcile against the record.
- `Durability.distinctRenamesFollowed` — the count, keyed on the renaming
  commit plus the path pair, which is the number that answers "how many
  renames did this walk cross".

`SpanLifespan.renamesFollowed` keeps its name, because per span it is accurate.

Two corrections to the first step the ledger entry had written for itself, both
found while building it:

- A `Set` of `renamedTo` values, which the entry proposed, undercounts. A file
  moved twice carries one `renamedTo` and would have counted as one rename. The
  identity is the commit plus the path pair, and `traceFile` now appends a
  `RenameCrossing` for each rename it actually reaches.
- The entry expected the change to touch `src/corroborate.ts` and a fixture
  record. Neither reads either field, so it touched `src/types.ts`,
  `src/lifespan.ts` and `src/lifespan.test.ts` only.

The emitted record now reads `"spanRenameCrossings": 3`,
`"distinctRenamesFollowed": 1`, for one `git mv`.

## 2. The ritual that ships the product has a name now

`ursa-major/dist/ursa.cjs` is committed, because GitHub hands an action to a
job as a tarball and the runner has no `npm install` step. On every repository
that is not this one, that file is the whole product.

The ledger asked for one script: `"regen": "npm run bundle && npm run
provenance:bundles"`. That chain cannot be correct in one pass, and this run
measured why:

1. `npm run bundle` on a dirty tree wrote the new bundle.
2. `npm run provenance:bundles` immediately after changed nothing, because
   `buildIndex` reads `git log` over the bundle path and the new digest was not
   committed yet.
3. After committing the bundle, `npm run provenance:bundles:check` printed
   `drifted:` for both index files.

So `npm run regen` is a converging command instead: it rebuilds the bundle,
tells the reader to commit it, and on the next invocation rewrites the index
that only becomes computable once that commit exists. `npm run regen:check`
verifies both and writes nothing. Four states, each one naming its next literal
command, with eight tests over them in `ursa-major/src/regen.test.ts`, because
the defect being prevented is a missing instruction and that is a property of
the strings.
