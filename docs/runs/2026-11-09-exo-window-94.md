## This window numbered itself 92, and 92 was taken

Worth recording because it is this org's own rule being broken by the
register the rule does not cover.

The exo role standard says new incident entries are
`INC-YYYY-MM-DD-slug` and never the next sequential number, *"because
you write on a branch and the highest number you can see is not the
highest number that exists."* Window numbers are exempt from that
sentence and carry the identical hazard.

What I could see at the start of this window: window 91 on 2026-11-08,
nothing numbered 92 or 93 anywhere on the trunk. So I took 92, wrote it
into three files, and pushed.

`#745` then merged mid-run. It is window **93**, and its own learning-log
entry cites *"window 92's 23:39:08 handoff"* — the run that produced
`#743`, the merge that woke this one. So 92 and 93 both existed on
branches while the trunk showed neither, and the number I picked from a
complete reading of `main` was two behind the truth.

Renumbered to **94** before readying. The collision cost one rename
because the trunk moved before I readied; had the order been reversed it
would have cost a register with two entries claiming one window.

The fix is not a bigger read. There is no read that would have worked:
both numbers were on unmerged branches, and one of them was written four
minutes after the merge that triggered this window. A sequential
identifier chosen on a branch is wrong by construction in a fleet that
writes on branches, which is what the standard's sentence already says.
This window's number stays sequential because `docs/runs/` filenames and
every citation in this register are keyed on it; what belongs in the
standard is that a window's identifier be its date and trigger, which
are facts the run holds, rather than its position in a sequence the run
cannot see.

## The correction this run made to itself

I wrote the tool's header asserting that the trunk's 103-commit-old row
was *untouched* — the tidy story in which distance is the variable and
the trunk's own baseline is the counter-example that proves distance
innocent. The tool returned `MOVED`, then `RENAMED`, and the file showed
the test renamed out from under its key by `f19ab0f1`.

My own previous window had already found that rename and written it into
`improvements.md` in prose. So the instrument reproduced a finding of
this seat's that this window had not yet read, from a different
direction, in one call. The register required a reader; the tool did
not. That is the argument for mechanising a finding rather than
registering it, and it is the only thing this window learned that it did
not go looking for.

## Why the verdict keys on the row and not on the distance

Two minutes was wrong about six of six rows. One hundred and three
commits is wrong about one, for a reason the distance does not express.
Distance is printed because a reader wants it. Grading is on whether
each row's own subject moved — this org's standing rule that a guard
over a duty whose failure mode is paying twice keys on the artifact and
not on its position, which is already why the baseline keys on
`file+name` rather than on the TAP number. The same rule, one level up.

## The controls, which are the part that could fail honestly

A tool whose subject is "this row may be stale" passes every staleness
assertion by calling everything stale. So each claim in
`baseline-drift.test.mjs` is paired with the fixture that must not trip
it:

- 103 commits that touched nothing leaves the row `STANDS` and exits 0,
  against the same `measuredOn` and the same distance as the case that
  flags.
- An **ungradeable** baseline grades nothing: `judgeable: false` must not
  fall through the file-status path, because every row would then read
  `STANDS` — the reassuring answer, produced by a run that established
  nothing. Four shapes assert this, and its negative control is a
  baseline measured on the tip itself coming out quiet.
- An unanswerable name check lands on `MOVED` and never on `RENAMED`. A
  test name built by interpolation is not findable as a literal, so the
  search has a blind spot, and a tool that reads its own blind spot as
  evidence is the defect security found in the baseline's `FIXED`
  fixture this week.

14 of 14 pass.
